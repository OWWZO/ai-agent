# Feature Specification: 对齐 free-code 的请求前会话压缩

**Feature Branch**: `[007-freecode-session-compaction]`  
**Created**: 2026-04-20  
**Status**: Draft  
**Input**: User description: "阅读 `D:\claude code\free-code-main` 的上下文压缩方案，并将当前会话压缩改为按每次请求开始前判断是否压缩；替换现有在请求完成后才 `refreshSessionMemory` 的触发时机，同时直接复用 free-code 的压缩思路和逻辑，淘汰当前简单字符串拼接摘要算法。"

## Existing System Context *(mandatory for brownfield features)*

- **Affected Modules**: `ai-agent-station-study-domain`、`ai-agent-station-study-app`
- **Existing Capabilities to Reuse**: 现有 `ai_agent_message / ai_agent_message_event / ai_agent_session_memory` 会话账本与快照、`AgentStreamPersistServiceImpl` 的请求装配入口、`AgentSessionMemoryServiceImpl` 的会话记忆服务、`SessionWorkingMemoryAssembler` 的请求级工作记忆重建、`SessionMemoryPromptFormatter` 的摘要注入、`SessionArtifactRestoreSupport` 的稳定文件恢复、`ReactorConfig` 的 session-memory 阈值配置、`006-session-context-memory` 已建立的 rich transcript 恢复能力
- **Out of Scope**: 不改前端历史展示交互、不把普通 `CHAT` 模式纳入本期、不引入跨会话用户长期记忆、不照搬 free-code 的 CLI `/compact` 交互、不迁移依赖特定 prompt-cache 能力的微压缩实现、不引入本地文件型 session-memory 目录作为新的真相源
- **Current Constraints**: MySQL 仍是会话历史与压缩快照的真相源；压缩快照需要版本化保留，运行时默认只消费最新有效快照；必须继续遵守 DDD 分层边界；已完成轮次与未完成轮次要严格区分；同一 `sessionId` 的模式冲突与并发守卫不能回退；历史重开与在线续聊必须共享同一套压缩语义；超长工具输出优先使用稳定引用或结构化关键信息，而不是整段回灌

## Clarifications

### Session 2026-04-20

- Q: 请求前压缩失败时，本轮请求应如何处理？ → A: 压缩失败时，若原始上下文仍在硬性安全上限内则降级继续；否则拒绝
- Q: 结构化会话记忆应如何生成？ → A: 每次需要压缩时，都由模型基于已有记忆和新增已完成历史直接重写或更新结构化会话记忆
- Q: 新生成的结构化会话记忆应如何持久化？ → A: 每次压缩成功后新增一条 MySQL 快照记录，运行时只使用最新一条，旧快照保留用于分析
- Q: 压缩后最近原始窗口的保留规则应以什么为主？ → A: 以 token 预算为主，并要求至少保留一个最小真实消息窗口，同时保持工具链完整

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 请求开始前自动判断并压缩 (Priority: P1)

作为在长会话中继续追问的用户，我希望系统在每次新请求真正进入模型之前，先判断当前上下文是否需要压缩，并在需要时先完成压缩后再继续本次请求，这样我不需要等到本轮结束后才“补做压缩”，也不会因为上下文已经过长而让下一轮失忆或失败。

**Why this priority**: 这是当前行为缺陷最直接的来源。压缩只在请求结束后触发，意味着真正需要压缩的那个“下一轮请求”并没有得到保护。

**Independent Test**: 构造一个已经接近或超过上下文阈值的 `REACT / PLAN_SOLVE` 会话，然后直接发起下一轮请求，验证系统会在主请求执行前完成“是否压缩”的判断，并能基于压缩后的上下文继续本轮任务。

**Acceptance Scenarios**:

1. **Given** 某会话的已完成历史已经达到压缩阈值，**When** 用户发起下一轮请求，**Then** 系统必须在本轮主执行开始前先完成压缩判断，并让本轮请求直接基于压缩后的上下文继续
2. **Given** 某会话历史仍低于压缩阈值，**When** 用户发起下一轮请求，**Then** 系统不得为了“固定流程”强行压缩，而应直接复用原始工作上下文
3. **Given** 某会话存在仍未完成、报错或被中断的历史轮次，**When** 用户发起下一轮请求，**Then** 这些未完成内容不得被错误纳入本次压缩源或已完成记忆

---

### User Story 2 - 会话压缩摘要升级为结构化工作记忆 (Priority: P2)

作为需要在多轮对话里持续推进复杂任务的用户，我希望压缩后的会话记忆能保留“当前在做什么、之前已经完成了什么、有哪些关键文件/结果/限制、下一步应继续什么”等结构化状态，而不是把历史简单拼成几句流水账。

**Why this priority**: 即使触发时机改到请求开始前，如果摘要内容仍然只是简单字符串拼接，压缩后依旧无法支撑复杂任务连续推进。

**Independent Test**: 构造一个包含任务说明、若干工具调用、错误修正、文件产物和阶段性结果的长会话，在触发压缩后继续追问“继续刚才的任务”“基于之前的结果补充”等指令，验证系统能从压缩后的记忆中恢复任务状态，而不是只知道若干旧问答。

**Acceptance Scenarios**:

1. **Given** 某会话已完成多轮复杂任务推进，**When** 会话被压缩后用户继续追问当前任务，**Then** 系统应能明确延续当前状态、关键结果和下一步，而不是退化为泛泛摘要
2. **Given** 某会话里已经出现关键文件、工具结果、错误修正与限制条件，**When** 历史被压缩后用户要求继续执行，**Then** 系统仍应保留这些关键工作记忆并用于后续决策
3. **Given** 某会话已存在较早的压缩记忆，**When** 新的已完成历史继续进入压缩流程，**Then** 系统应在原有结构化记忆上增量更新，而不是简单把新旧轮次全文串接

---

### User Story 3 - 压缩后仍保留最近真实上下文与调用关系 (Priority: P3)

作为在压缩后继续追问最近操作细节的用户，我希望系统在保留结构化历史记忆的同时，仍然保留足够的最近原始上下文，而且不能打断最近的工具调用链、结果对应关系和关键推理片段，否则我继续追问时会得到错乱的上下文。

**Why this priority**: free-code 的压缩价值不只在“有摘要”，还在于“摘要 + 最近窗口”共同组成可继续工作的上下文，并且不会破坏工具链顺序。

**Independent Test**: 构造一个包含重复工具调用、超长输出、连续推理和最近多轮追问的长会话，在触发压缩后立刻追问最近一步的结果或下一步计划，验证系统既能引用结构化会话记忆，也能正确保留最近原始上下文与调用顺序。

**Acceptance Scenarios**:

1. **Given** 某会话最近窗口内存在连续的工具调用与结果，**When** 用户在压缩后继续追问最近一步操作，**Then** 系统必须保留这些最近上下文及其正确顺序
2. **Given** 某会话最近窗口内存在同一工具的多次调用，**When** 历史被压缩后用户追问其中某次调用结果，**Then** 系统不得把不同调用的结果混淆或错误配对
3. **Given** 某会话中存在超长报告、长命令输出或大段文件差异，**When** 系统执行压缩，**Then** 它应保留关键结果和稳定引用，并保证最近窗口仍然可用于继续工作

### Edge Cases

- 会话已达到压缩阈值，但可用的压缩记忆尚未准备好、正在刷新或边界信息失效时，系统必须安全降级，不能构造损坏的上下文
- 压缩后保留最近窗口时，不能拆断 `tool_use` 与对应 `tool_result`，也不能丢失与保留消息属于同一逻辑轮次的关键推理片段
- 如果连续多次压缩尝试都失败，系统不能在每次新请求都无限重复进行注定失败的压缩尝试
- 请求前压缩失败时，若原始上下文仍未超过硬性安全上限，则系统应降级继续本轮请求；只有在上下文仍超限或已损坏时才拒绝
- 历史重开后若最近窗口与压缩边界无法直接对齐，系统仍需保证上下文连续性，而不是让重开后的第一轮请求失忆
- 长报告、超长 `stdout/stderr`、大 `diff` 或类似输出不能因为压缩而完全失去可追溯性，至少要保留关键结果和稳定引用
- `STREAMING / ERROR / FORCE_STOPPED` 轮次不得被当成已完成事实写入结构化会话记忆
- 若同一 `sessionId` 发生模式冲突或会话并发执行，系统仍需先执行现有守卫，而不是让自动压缩绕过这些保护

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 在每次新的 `REACT / PLAN_SOLVE` 请求开始前，基于当前会话的可复用历史上下文执行一次“是否需要压缩”的判断
- **FR-002**: 系统 MUST NOT 把“请求完成后刷新会话记忆”作为唯一压缩时机；请求结束后的处理至多只能用于准备或更新压缩记忆素材，真正决定是否压缩本轮请求的时机必须发生在下一轮请求开始前
- **FR-003**: 压缩触发判断 MUST 使用与实际请求装配一致的上下文规模口径，确保阈值判断反映真实的可用上下文窗口，而不是仅凭粗糙的事后估算
- **FR-004**: 当需要压缩时，系统 MUST 优先采用“结构化会话记忆 + 最近保留窗口”的组合上下文，而不是继续沿用当前简单字符串拼接摘要
- **FR-005**: 结构化会话记忆 MUST 能表达至少以下语义：当前状态、任务目标/任务说明、关键文件或产物、关键工作流、错误与修正、重要系统知识、关键结果以及近期工作轨迹
- **FR-006**: 结构化会话记忆 MUST 在每次需要压缩时由模型基于已有记忆和新增已完成历史直接重写或更新，而不是继续依赖简单规则拼接或沿用旧版字符串摘要
- **FR-006A**: 结构化会话记忆 MUST 能在已有历史记忆基础上持续增量更新，而不是每次压缩都把新旧轮次简单串接成流水账
- **FR-007**: 系统 MUST 在压缩后保留一个最近原始上下文窗口，使用户能够继续追问最近几步的真实执行链，而不是只剩压缩摘要；该窗口应以 token 预算为主进行裁剪
- **FR-008**: 最近保留窗口 MUST 在 token 预算约束下至少保留一个最小真实消息窗口，并保持工具调用、工具结果、重复调用顺序以及关键推理片段的关联关系，不能因压缩而打断这些因果链
- **FR-009**: 系统 MUST 只把已完成轮次纳入结构化会话记忆和请求前压缩决策，未完成、报错或被强停的轮次 MUST NOT 进入可复用压缩上下文
- **FR-010**: 对长报告、超长命令输出、大段差异或其他超长原始结果，系统 MUST 以关键结果和稳定引用为主进行保留，而不是在压缩记忆或最近窗口中无边界追加全文
- **FR-011**: 当压缩记忆缺失、边界失效、压缩收益不足或压缩过程中发生异常时，系统 MUST 采用明确定义的安全回退策略；若原始上下文仍在硬性安全上限内则降级继续本轮请求，否则拒绝请求，避免生成损坏上下文
- **FR-012**: 当同一会话连续发生压缩失败时，系统 MUST 具备失败节流或暂停重试机制，避免每次新请求都重复执行注定失败的压缩
- **FR-013**: 请求前压缩行为 MUST 继续复用现有会话记忆主链路统一承载，确保压缩判断、工作记忆重建和请求装配在同一条会话语义链路内完成，而不是散落在多个入口各自处理
- **FR-014**: 系统 MUST 保持历史重开与在线续聊使用相同的压缩语义，使被压缩的会话在重开后的第一轮请求中仍能恢复相同的结构化记忆与最近窗口
- **FR-015**: 系统 MUST 继续保留现有模式冲突、会话忙碌和会话账本约束；自动压缩不得绕过这些既有保护
- **FR-016**: 系统 MUST 明确现有会话记忆快照、压缩边界、更新节奏和阈值配置如何演进，并在优先复用现有存储与配置契约的前提下补齐请求前压缩所需的最小兼容调整
- **FR-016A**: 每次压缩成功后，系统 MUST 新增一条新的会话记忆快照记录，而不是直接覆盖上一条快照；运行时默认只加载最新有效快照，旧快照继续保留用于分析和回溯
- **FR-017**: 系统 MUST 让本次压缩方案在行为上对齐 `free-code-main` 的核心思路，即“请求入口判断、优先使用会话记忆压缩、保留最近真实上下文、失败时安全回退”，而不是仅复制其表面摘要文本格式

### Key Entities *(include if feature involves data)*

- **Compaction Decision**: 每次新请求开始前，根据当前会话上下文规模、会话状态与压缩素材可用性得出的“是否压缩”判定结果
- **Structured Session Memory**: 面向长会话连续工作的结构化记忆载荷，由模型基于已有记忆与新增已完成历史重写或更新，承载当前状态、任务目标、关键文件、错误修正、关键结果和工作轨迹等核心信息
- **Session Memory Snapshot Version**: 某次压缩成功后落库的一版完整会话记忆快照；运行时默认读取最新有效版本，历史版本保留用于分析与回溯
- **Summarized Boundary**: 已被结构化会话记忆覆盖的历史边界，用于区分“已压缩历史”和“仍需保留的最近原始窗口”
- **Preserved Recent Window**: 在压缩后仍以原始上下文形式保留的最近历史片段，用于支撑对最近步骤、工具链和推理片段的继续追问
- **Recent Window Budget**: 用于决定最近原始窗口保留范围的预算规则，以 token 预算为主，同时约束最小真实消息窗口和工具链完整性
- **Compaction Guardrail State**: 与压缩相关的保护状态，包括素材是否可用、是否存在未完成轮次、连续失败次数以及是否允许继续尝试压缩

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在达到压缩阈值的验收样本中，100% 的下一轮请求都能在不需要用户重述历史的前提下继续推进任务，而不是等到本轮结束后才补做压缩
- **SC-002**: 在包含任务状态、工具执行、错误修正和文件产物的长会话样本中，95% 以上的压缩后续聊都能正确延续“当前在做什么、已经完成什么、下一步做什么”
- **SC-003**: 在包含重复工具调用和最近连续操作的验收样本中，100% 的压缩后续聊都不会出现最近调用顺序错乱或结果错误配对
- **SC-004**: 与当前简单摘要行为相比，在长会话续聊样本中，由于上下文丢失导致的重复工具执行比例降低至少 80%
- **SC-005**: 在包含超长输出或长报告的验收样本中，100% 的压缩后上下文都能保留可复用的关键结果与稳定引用，同时让下一轮请求继续成功执行

## Assumptions

- 本期范围聚焦于 `REACT / PLAN_SOLVE` 会话主链路，普通 `CHAT` 模式仍沿用现有滑动窗口策略
- 现有 `ai_agent_session_memory` 与会话账本能力足以承载这次“free-code 风格”压缩迁移，除非发现明确缺口，否则优先做兼容演进而不是另起一套存储
- `006-session-context-memory` 已建立的 rich transcript 恢复能力是本期的输入前提，本期在其上补齐“请求前压缩决策”和“高质量会话记忆”两部分
- free-code 的文件型 session memory、CLI 交互和依赖特定平台能力的微压缩细节不会原样照搬；真正迁移的是其请求时机、结构化记忆、最近窗口和安全回退思路
- 对于超长工具结果，现有稳定文件/产物引用机制可以继续承担“压缩后可追溯”的职责
- 每次需要压缩时，系统允许同步调用模型来生成或更新结构化会话记忆，只要它遵守本规格定义的安全上限与回退策略
- 现有会话记忆存储契约允许演进为“同一会话多版本快照”，只要运行时仍能稳定选择最新有效版本参与请求装配
