# Feature Specification: ReAct / PlanSolve 会话上下文记忆

**Feature Branch**: `[006-session-context-memory]`  
**Created**: 2026-04-18  
**Status**: Draft  
**Input**: User description: "为 ReAct 和 PlanSolve 实现类似 free-code-main 的会话上下文记忆机制：基于 MySQL 持久化会话消息、自动压缩长历史、重建工作消息上下文，并让历史记忆在单会话内持续生效"

## Existing System Context *(mandatory for brownfield features)*

- **Affected Modules**: `ai-agent-station-study-domain`、`ai-agent-station-study-infrastructure`、`ai-agent-station-study-trigger`、`ai-agent-station-study-app`
- **Existing Capabilities to Reuse**: 现有 `ai_agent_conversation / ai_agent_message / ai_agent_message_event` 持久化链路、`AgentStreamPersistServiceImpl` 消息与事件落库能力、ReAct 与 PlanSolve 执行节点、Prompt 模板中的 `history_dialogue` 占位符、现有会话列表与详情接口、现有 `sessionId` 会话标识
- **Out of Scope**: 不引入 Spring AI 自带 ChatMemory 插件、不改造成基于 Markdown 的长期记忆文件、不新增跨用户共享记忆、不重做普通 `CHAT` 模式的历史机制、不追求逐 token 历史回放
- **Current Constraints**: 记忆真相源必须落在 MySQL；需要保持 DDD 模块边界清晰；必须兼容当前流式输出与历史会话体系；ReAct 与 PlanSolve 需要复用同一套会话记忆装配思想；长会话不能无限拼接全量历史而导致上下文失控

## Clarifications

### Session 2026-04-19

- Q: 文件上下文恢复应采用什么策略？ → A: 恢复稳定文件或产物引用，并在同一 `sessionId` 续聊时重新作为可用文件上下文
- Q: 同一会话并发请求应如何处理？ → A: 同一 `sessionId` 禁止并发，请求冲突时直接提示用户等待或先停止当前轮次
- Q: 压缩摘要应采用什么持久化形态？ → A: 每个 `sessionId` 只保留一份当前生效的摘要快照，后续压缩时原地更新
- Q: 异常或强制停止轮次应如何进入会话记忆？ → A: 消息状态为 `ERROR / FORCE_STOPPED` 的轮次完全不进入会话记忆
- Q: 同一会话切换模式时应如何处理？ → A: 同一 `sessionId` 不允许切换模式，切换 `REACT / PLAN_SOLVE` 时必须新建会话

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 同一会话持续记住上下文 (Priority: P1)

作为在同一会话里持续追问的用户，我希望 ReAct 和 PlanSolve 在后续轮次里能够记住我之前给出的目标、约束、偏好和中间结论，而不是每一轮都像新问题重新开始。

**Why this priority**: 这是会话记忆的核心价值。如果同一 `sessionId` 下的上下文不能连续保留，深度思考和深度研究都会显著退化。

**Independent Test**: 在同一会话中连续发送多轮问题，前一轮中明确给出格式要求、分析边界或关注重点；后续轮次无需重复说明，系统仍应继续遵循这些上下文约束。

**Acceptance Scenarios**:

1. **Given** 用户在同一会话第一轮中声明输出格式、分析对象和关键限制，**When** 用户在下一轮继续追问，**Then** 系统应基于同一会话的上下文继续回答，而不是丢失之前的约束
2. **Given** 同一会话已经完成过一次 `PLAN_SOLVE` 任务规划或一次 `REACT` 研究过程，**When** 用户要求继续补充、修正或延伸结果，**Then** 系统应能利用前序轮次中的关键信息继续推理
3. **Given** 用户希望从 `REACT` 切换到 `PLAN_SOLVE`，或从 `PLAN_SOLVE` 切换到 `REACT`，**When** 用户继续提交新问题，**Then** 系统应要求其新建会话，而不是在原 `sessionId` 上混用两种模式

---

### User Story 2 - 长会话自动压缩但不丢关键语义 (Priority: P2)

作为持续进行深度任务的用户，我希望当会话历史很长时，系统能够自动压缩早期内容，只保留摘要、关键事实和最近的详细上下文，从而既不超过模型上下文限制，也不丢失真正重要的信息。

**Why this priority**: 只要会话足够长，单纯拼接完整历史就一定会失控。没有自动压缩，记忆机制只能在短对话中工作。

**Independent Test**: 构造一个超过上下文阈值的长会话，验证系统仍可继续执行后续轮次，并保持对前序核心结论、用户约束和当前任务状态的正确理解。

**Acceptance Scenarios**:

1. **Given** 某个会话已经累积大量历史消息，**When** 系统准备处理新一轮输入，**Then** 系统应优先保留压缩摘要、关键事实与最近若干轮完整消息，而不是无上限拼接全部历史
2. **Given** 某个长会话已经发生过一次自动压缩，**When** 用户继续追问之前讨论过的核心结论，**Then** 系统仍应基于压缩后的记忆正确延续对话

---

### User Story 3 - 历史会话重开后仍能继续记忆 (Priority: P3)

作为回到旧会话继续工作的用户，我希望重新打开历史会话后，后续输入仍能基于这个会话已保存的上下文继续进行，而不是只看到历史展示，真正提问时却丢失之前的上下文。

**Why this priority**: 单会话记忆不应只存在于进程内存。只要会话已经落库，重新进入同一 `sessionId` 时就应该恢复工作记忆。

**Independent Test**: 完成一段 `REACT` 或 `PLAN_SOLVE` 会话后，重新进入该会话并继续提问，验证系统会基于该会话已持久化的摘要与最近历史继续执行。

**Acceptance Scenarios**:

1. **Given** 某个已存在的历史会话已经保存了多轮消息与压缩摘要，**When** 用户重新进入该会话并继续提问，**Then** 系统应从持久化记忆中重建工作上下文并继续回答
2. **Given** 某个历史会话包含文件、计划或中间结论等关键上下文，**When** 用户在后续轮次基于这些内容继续追问，**Then** 系统应能够恢复这些关键上下文的可用表示，其中稳定文件或产物引用应重新作为可用文件上下文参与后续执行

### Edge Cases

- 会话存在但历史消息为空时，系统应安全退化为“仅使用当前输入”的新会话执行
- 同一 `sessionId` 下若上一轮仍在执行，新请求不能与其并发写入同一份会话记忆，系统必须返回明确冲突提示并要求用户等待完成或先停止当前轮次
- 同一会话历史中如果存在异常中断、失败或强制停止轮次（对应消息状态 `ERROR / FORCE_STOPPED`），系统必须将这些轮次排除在会话记忆重建与压缩摘要之外，避免无效中间态污染后续续聊
- 长会话经过多次压缩后，系统仍应保留压缩边界与最近详细历史，避免摘要反复摘要导致语义漂移
- 历史消息中若包含大段工具输出、搜索结果或文件解析内容，系统应优先提取可复用的用户语义与关键事实，而不是机械拼接大文本
- ReAct 与 PlanSolve 共享记忆装配链路时，不能污染各自已有的执行协议和提示词职责边界
- 当请求里携带的 `sessionId` 与持久化链路使用的会话标识不一致时，系统必须以真实会话标识为准，避免记忆串话或读不到历史
- 同一 `sessionId` 若尝试在 `REACT` 与 `PLAN_SOLVE` 之间切换，系统必须拒绝复用原会话并明确要求新建会话，避免两种模式的提示词、任务协议与记忆语义互相污染

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 以 `sessionId` 作为 ReAct 与 PlanSolve 单会话记忆的唯一归属标识，并确保执行链路、持久化链路和历史读取链路使用同一个会话标识
- **FR-002**: 系统 MUST 在每次新请求开始前，从当前会话的持久化历史中重建一份“工作消息上下文”，作为本轮推理输入的一部分
- **FR-003**: 系统 MUST 让这份工作消息上下文同时包含当前会话的压缩摘要、关键事实和最近若干轮详细消息，而不是只读取最后一轮结果
- **FR-004**: 系统 MUST 为 ReAct 与 PlanSolve 提供统一的会话记忆装配入口，避免两条执行链路各自维护一套完全独立的历史拼接逻辑
- **FR-004A**: 系统 MUST 保持单个 `sessionId` 的模式归属唯一；一旦会话已绑定 `REACT` 或 `PLAN_SOLVE`，后续若用户切换到另一种模式，系统必须要求新建会话，而不是沿用原会话记忆
- **FR-005**: 系统 MUST 继续复用现有 MySQL 会话、消息和事件持久化体系作为单会话记忆的真相源，而不是引入新的文件型会话记忆机制
- **FR-006**: 系统 MUST 在会话历史过长时自动生成可持久化的压缩摘要，并记录其适用边界，使后续轮次可以在摘要基础上继续累积记忆
- **FR-006A**: 系统 MUST 对每个 `sessionId` 仅维护一份当前生效的会话记忆摘要快照，并在后续压缩时原地更新摘要内容与压缩边界，而不是长期维护多版本摘要历史
- **FR-007**: 系统 MUST 保留最近若干轮完整消息作为压缩后的详细窗口，以维持当前任务阶段的上下文细节
- **FR-007A**: 系统 MUST 在历史重开续聊时恢复同一 `sessionId` 下的稳定文件或产物引用，并将其重新作为可用文件上下文参与后续轮次执行，而不是只保留文字摘要
- **FR-008**: 系统 MUST 在压缩摘要中保留用户目标、输出约束、关键事实、已完成结论、当前任务状态和后续待续上下文等高价值信息
- **FR-009**: 系统 MUST 避免把纯工具噪音、重复观察文本或大体量原始结果无差别写入工作消息上下文，防止无效内容占满模型窗口
- **FR-009A**: 系统 MUST 将消息状态为 `ERROR / FORCE_STOPPED` 的轮次排除在会话记忆摘要、关键事实提炼和工作消息重建之外，不得把未完成轮次内容继续作为后续续聊的会话记忆输入
- **FR-010**: 系统 MUST 让会话重开后的新请求能够基于数据库中已保存的摘要与最近历史恢复工作记忆，而不是依赖单次进程内缓存
- **FR-011**: 系统 MUST 通过已有 Prompt 装配链路把会话记忆注入到 ReAct 与 PlanSolve 的系统上下文或历史对话占位区中，且注入方式对调用方透明
- **FR-012**: 系统 MUST 为压缩摘要记录明确的覆盖范围或边界位置，避免后续再次压缩时重复处理已归档的历史消息
- **FR-012A**: 系统 MUST 禁止同一 `sessionId` 在上一轮尚未结束时并发发起新的续聊请求，并返回明确的冲突提示，引导用户等待完成或先停止当前轮次
- **FR-013**: 系统 MUST 明确本次新增或变更的数据契约，包括会话记忆摘要、压缩边界、关键事实或相关元数据的持久化结构
- **FR-014**: 系统 MUST 在不改变用户已有会话列表与详情使用方式的前提下，为后续轮次执行补齐上下文记忆能力
- **FR-015**: 系统 MUST 使 ReAct 与 PlanSolve 在相同会话记忆策略下达到接近 `free-code-main` 的效果：短会话带完整上下文，长会话带摘要加最近详细窗口，历史重开后仍可继续记忆

### Key Entities *(include if feature involves data)*

- **Session Working Memory**: 单次请求开始前从持久化历史重建出的工作上下文，供 ReAct 或 PlanSolve 在本轮执行时直接消费
- **Session Memory Summary**: 针对某个会话早期历史生成的压缩摘要，保存用户目标、约束、关键结论、阶段状态与高价值事实
- **Active Session Memory Snapshot**: 每个 `sessionId` 当前唯一生效的摘要快照，随压缩推进持续更新，是工作记忆重建时优先读取的压缩视图
- **Session Memory Fact**: 从多轮历史中沉淀出的结构化关键事实，例如固定输出要求、明确偏好、确认过的业务结论或任务边界
- **Session Memory Boundary**: 压缩摘要所覆盖到的历史边界，用于标识哪些历史已经被摘要吸收、哪些历史仍需要按详细消息直接参与上下文重建
- **Recent Conversation Window**: 当前会话中保留详细内容的最近若干轮消息窗口，用于维持短期上下文连续性
- **Session Artifact Reference**: 会话内可长期解析的文件或产物引用，在历史会话重开续聊时需要重新进入可用文件上下文，而不是只作为展示信息存在

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在验收样本中，100% 的同会话连续追问场景都能继承前序轮次中已明确的目标、约束或偏好，而无需用户重复说明
- **SC-002**: 在验收样本中，长会话进入压缩后仍能继续完成后续追问，且不会因为历史过长直接失败或明显遗忘核心结论
- **SC-003**: 在验收样本中，100% 的历史重开续聊场景都能基于已保存的会话记忆继续执行，而不是退化成无上下文的新会话
- **SC-004**: 对超长会话样本，压缩后进入模型上下文的会话记忆载荷（以 `estimatedTokens` 或等价字符数估算）应不高于未压缩全量历史的 40%，且至少保留最近 2 轮完整 `user / assistant` 详细消息
- **SC-005**: ReAct 与 PlanSolve 共用同一套会话记忆装配与压缩策略后，两种模式都必须在“连续追问”“长会话”“历史重开续聊”三类场景中各至少通过 1 组独立验收样本

## Assumptions

- 本次优先解决单会话上下文记忆，不在本需求内引入跨会话用户画像或跨项目长期偏好体系
- 会话级历史真相源继续使用 MySQL，且现有消息与事件表已经能够提供足够的轮次信息用于记忆重建
- 压缩摘要与关键事实允许新增持久化结构，但不应破坏现有会话列表、详情与流式链路的主职责
- 会话级压缩摘要只需要维护当前生效快照，不要求保留多版本摘要历史用于回溯
- 只有已完成的稳定轮次才有资格进入会话记忆；失败与强制停止轮次仅保留原始历史展示价值，不参与续聊记忆重建
- 单个会话的模式归属保持稳定，不考虑在同一 `sessionId` 内跨 `REACT / PLAN_SOLVE` 混合续聊
- Prompt 模板中的 `history_dialogue` 已经是合适的记忆注入位置之一，可在现有装配链路上复用
- 当前 UI 已经能够稳定传递同一标签页内复用的 `sessionId`，后端需要补齐的是基于该 `sessionId` 的记忆恢复与压缩
- 历史会话涉及的文件与产物已经拥有稳定引用标识，允许在同一 `sessionId` 续聊时重新装配为可用文件上下文
- 压缩策略的目标是保留可继续工作的语义记忆，不是恢复完整逐步回放日志
