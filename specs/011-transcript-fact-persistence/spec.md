# Feature Specification: 后端事实对话账本重构

**Feature Branch**: `[011-transcript-fact-persistence]`  
**Created**: 2026-04-26  
**Status**: Draft  
**Input**: User description: "把当前对话历史持久化重构为按后端事实落库：MySQL 里只存后端产生的事实，不存前端运行时信息；历史重开时由后端从 MySQL 查询事实并重新投影成与实时对话相同的渲染契约，前端展示效果保持不变。旧历史数据可直接清理，不做兼容。上传文件与本轮生成文件需要分开存，其中本轮生成文件要能直接从消息表查询。"

## Existing System Context *(mandatory for brownfield features)*

- **Affected Modules**: `ai-agent-station-study-domain`、`ai-agent-station-study-trigger`、`ai-agent-station-study-app`、`ui`
- **Existing Capabilities to Reuse**: 现有 `ai_agent_conversation / ai_agent_message / ai_agent_message_event` 三层账本、`AgentStreamPersistServiceImpl` 流式持久化入口、`ConversationReplayAssembler` 历史详情装配、`SessionTranscriptBlockAssembler` 与 `SessionWorkingMemoryAssembler` 会话上下文恢复、现有稳定文件引用能力、现有实时对话渲染契约
- **Out of Scope**: 不改上游 SSE 协议、不新增独立文件表、不保留旧历史数据兼容读取、不改变前端实时对话视觉结构、不引入跨会话长期用户画像
- **Current Constraints**: MySQL 仍是会话历史与续聊上下文的真相源；必须遵守 DDD 分层边界；历史读取必须只依赖后端已持久化事实；大体量文件正文或报告正文不能重新内联回数据库；已存在的上传文件与生成文件需要分开表达

## Clarifications

### Session 2026-04-26

- Q: 历史持久化的目标应该是什么？ → A: 让后端记住之前的对话事实，而不是为了前端回放去保存一份前端运行时快照
- Q: 历史重开后的前端展示应该如何处理？ → A: 前端展示效果保持不变，区别只在于数据来源从“实时后端推送”变成“后端查库后再投影”
- Q: 本轮生成文件应该存在哪里？ → A: `ai_agent_message` 单独新增字段保存本轮生成文件摘要，便于按会话或轮次直接查询
- Q: 上传文件与生成文件是否混存？ → A: 不混存，`files_json` 继续表示上传文件，生成文件单独存字段
- Q: 旧历史数据如何处理？ → A: 不做兼容，允许上线前直接清理
- Q: 是否新增独立文件表？ → A: 不新增，继续复用现有消息表和事件表承接事实账本

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 重开历史时复现与实时一致的最终结果 (Priority: P1)

作为回看历史会话的用户，我希望重新打开一条已完成的深度思考或深度研究对话时，页面看到的最终结果、关键步骤和文件入口与当时对话结束时保持一致，而不是因为历史读取改走数据库后出现内容缺失或结构变化。

**Why this priority**: 这是本次重构的首要价值。若历史重开后的可见结果与实时结束态不一致，后端事实化落库就没有业务意义。

**Independent Test**: 分别完成一条 `PLAN_SOLVE` 与一条 `REACT` 会话，记录结束时页面可见的最终答案、关键细节块和文件入口；刷新页面并重新打开该会话，确认历史详情仍呈现同样的最终可见结果。

**Acceptance Scenarios**:

1. **Given** 一条结构化会话已经完成并展示了最终答案、关键过程块和文件入口，**When** 用户刷新页面后重新打开该会话，**Then** 历史详情必须复现这些最终可见结果，而不是退化为另一套历史专用视图
2. **Given** 一条会话在结束时生成了 HTML、Markdown、PPT 或其他文件入口，**When** 用户从历史详情中再次查看该会话，**Then** 前端必须还能看到同类入口并按既有方式预览或下载
3. **Given** 一条会话以错误或强制停止结束，但结束前已经产生了部分可见结果，**When** 用户重新打开历史，**Then** 页面仍应展示这些已产生的事实并明确标识终态

---

### User Story 2 - 同会话续聊时恢复后端事实记忆 (Priority: P2)

作为继续在同一会话里工作的用户，我希望系统在下一轮请求开始前能够基于数据库中保存的用户输入、思考、工具调用、工具结果和文件引用恢复上下文，而不是依赖前端临时状态或一份前端快照化事件模型。

**Why this priority**: 用户真正需要的是“系统记住做过什么”。如果历史只满足展示而不能作为续聊工作记忆，当前设计仍然没有解决核心问题。

**Independent Test**: 在同一会话中先完成一轮包含工具调用和文件产物的复杂任务，再发起“继续刚才任务”的下一轮请求，验证系统能感知上一轮已经完成的事实与生成文件，而不是只记住问题和最终回答。

**Acceptance Scenarios**:

1. **Given** 某轮对话已经执行过搜索、工具调用并生成了文件，**When** 用户在同一会话里要求“继续刚才的分析”，**Then** 系统必须基于数据库中保存的事实继续工作，而不是重新从零开始
2. **Given** 某轮对话已经生成了可复用文件，**When** 用户在下一轮要求基于该文件继续修改或补充，**Then** 系统必须能从该轮消息账本中直接恢复这些生成文件摘要和稳定引用
3. **Given** 某轮历史缺少某个可选展示块，但主事实账本完整，**When** 系统构建下一轮上下文，**Then** 它应优先依赖后端事实账本恢复而不是因为缺少前端样式化信息导致续聊失败

---

### User Story 3 - 开发者能按后端模型演进历史账本 (Priority: P3)

作为维护对话系统的开发者，我希望历史持久化围绕“后端事实账本”来设计，让消息表保存轮次级摘要，事件表保存有序语义块，前端展示只在读取期投影生成，这样后续新增展示块或文件类型时不需要再把前端运行时字段直接塞进数据库。

**Why this priority**: 这是本次重构能否长期可维护的关键。如果数据库继续围绕前端快照扩张，历史、续聊和文件查询都会继续耦合在一起。

**Independent Test**: 以现有 `PLAN_SOLVE / REACT` 场景为样本，验证新增一个历史细节块类型时，只需补充后端事实块映射和历史投影规则，而不需要再新增一批前端专用持久化字段。

**Acceptance Scenarios**:

1. **Given** 后端新增一种新的结构化结果块，**When** 该结果块需要进入历史详情与续聊上下文，**Then** 系统应通过扩展后端事实块类型和投影规则完成支持，而不是新增一组前端快照字段
2. **Given** 需要按会话查看某轮生成过哪些文件，**When** 开发者查询消息账本，**Then** 应能直接从消息表字段获取生成文件摘要，而不必先解析事件载荷
3. **Given** 某个文件型结果正文体量较大，**When** 系统持久化该轮事实，**Then** 数据库中只保留稳定引用和必要元数据，而不是重复存储全文

### Edge Cases

- 一轮会话没有生成任何文件时，消息表中的生成文件字段必须为空或空集合，不能伪造默认值
- 同一轮会话生成多个同类型文件时，消息表中的生成文件字段必须完整保留所有文件摘要，不能只保留第一项
- 某个事件块引用的外部文件已失效或不可访问时，历史详情必须返回明确缺失状态，而不是假装文件存在
- 某轮会话仅有最终回答，没有额外工具或过程块时，历史详情仍必须能正确渲染轻量结果
- 同一轮里出现多个同类工具调用或结果块时，事件账本必须保留顺序与关联关系，避免重放或续聊时错配
- 旧历史数据在切换前被清理后，系统只需要保证新写入账本可用，不应再尝试兼容旧结构

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 只把后端在一次对话执行过程中真实产生的事实持久化到 MySQL，包括用户输入、最终回答、过程块、工具调用、工具结果、文件引用、状态和必要指标
- **FR-002**: 系统 MUST NOT 把前端运行时产生的临时信息作为历史真相源写入 MySQL，包括仅服务于前端本地状态合并、占位、展开收起或列表回放的临时字段
- **FR-003**: 系统 MUST 继续使用 `ai_agent_message` 作为单轮请求账本，保存该轮的请求标识、用户输入、上传文件、生成文件摘要、最终回答、执行状态、基础指标与时间信息
- **FR-004**: 系统 MUST 将上传文件与本轮生成文件分开存储，其中 `files_json` 仅表示上传文件，生成文件必须存入独立字段并可直接按消息或会话查询
- **FR-005**: 系统 MUST 继续使用 `ai_agent_message_event` 作为单轮内的有序事实块账本，每条记录表达一个后端语义块，而不是一份面向前端的整块回放快照
- **FR-006**: 系统 MUST 为事实块定义清晰且稳定的类型语义，至少覆盖用户输入、助手思考、计划/任务推进、工具调用、工具结果、文件引用与最终回答等历史与续聊所需事实
- **FR-007**: 系统 MUST 让事件账本中的载荷只保存该语义块的事实数据、稳定资源引用和必要渲染元数据，不再以内联全文方式长期保存可由稳定引用获取的大体量内容
- **FR-008**: 系统 MUST 在历史详情读取时，从消息账本与事件账本恢复后端事实，再投影成与实时对话相同的渲染契约供前端使用
- **FR-009**: 系统 MUST 让“实时对话渲染”和“历史详情渲染”共享同一份后端输出契约；两者差异只能体现在数据来源，而不是前端另写一套历史专用展示协议
- **FR-010**: 系统 MUST 让会话工作记忆恢复依赖消息账本与事件账本中的后端事实，而不是依赖前端快照模型或前端本地状态
- **FR-011**: 系统 MUST 保留同一轮中多个事实块的顺序和关联关系，使历史详情展示与续聊上下文恢复都能反映真实执行顺序
- **FR-012**: 系统 MUST 在生成文件、报告或其他大体量产物时，只把可长期访问的稳定资源标识、预览/下载入口与必要文件元数据纳入消息账本或事件账本
- **FR-013**: 系统 MUST 在稳定资源不可访问时返回明确的缺失状态或错误状态，以便前端按现有交互向用户说明原因
- **FR-014**: 系统 MUST 允许上线时直接清理旧历史数据，本次重构不承担旧数据结构到新模型的兼容读取责任
- **FR-015**: 系统 MUST 保持历史列表接口继续返回轻量会话摘要，不因事实化账本重构而把整轮细节或大体量文件内容带入列表读取
- **FR-016**: 系统 MUST 明确后端职责边界：`domain` 负责事实归档、记忆恢复与历史投影，`trigger` 负责会话/详情查询契约，`app` 负责表结构与 Mapper 落地，`ui` 继续复用既有渲染链路

### Key Entities *(include if feature involves data)*

- **Conversation Summary**: 面向历史列表的轻量会话信息，包含会话身份、标题、模式、预览、排序时间与消息计数
- **Conversation Turn Ledger**: 一轮用户请求的主账本，保存用户输入、上传文件、生成文件摘要、最终回答、状态、指标与时间信息
- **Transcript Fact Block**: 从属于某轮请求的一条有序后端事实块，用于表达思考、计划、工具调用、工具结果、文件引用或其他结构化执行事实
- **Generated File Summary**: 某轮执行过程中产生的文件摘要集合，包含文件名称、稳定资源标识、预览入口、下载入口、类型、大小等可查询元数据
- **Artifact Reference**: 指向 HTML、Markdown、PPT、代码文件或其他结果产物的稳定引用，支持历史详情展示与续聊上下文恢复
- **History Projection**: 后端在读取消息账本与事实块账本后，重新装配出的统一渲染契约，用于给前端回显与实时一致的最终效果

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在验收样本中，100% 的已完成 `PLAN_SOLVE` 与 `REACT` 会话在刷新后重新打开时，都能展示与对话结束时一致的最终答案、关键细节块与文件入口
- **SC-002**: 在同会话续聊验收样本中，100% 的下一轮请求都能基于数据库中保存的后端事实恢复上下文，而不是依赖前端临时状态
- **SC-003**: 对于包含生成文件的验收样本，100% 的会话都可以直接通过消息账本字段查询出本轮生成文件摘要，而不需要解析事件载荷
- **SC-004**: 对大体量 HTML、Markdown、PPT 或报告类产物，新的历史持久化不再把正文全文重复写入事件载荷；数据库中只保留稳定引用和必要元数据
- **SC-005**: 在验收样本中，历史列表首屏仍只依赖轻量会话摘要即可完成加载，不需要额外读取完整事实块账本
- **SC-006**: 新增一种历史细节块类型时，开发者只需扩展后端事实块映射与历史投影规则即可完成支持，不需要再新增前端临时状态型持久化字段

## Assumptions

- 现有实时对话输出契约已经足够稳定，可作为历史详情投影的目标契约继续复用
- 现有文件服务或稳定资源引用能力可以提供长期可访问的 `resourceKey`、预览入口和下载入口
- 本轮生成文件只需要在消息账本中保存轻量摘要，不需要把文件正文同步写入数据库
- 旧历史数据会在上线切换前被清理，因此可以直接按新模型重写持久化与读取链路
- 本次重构优先覆盖 `PLAN_SOLVE` 与 `REACT` 历史/续聊主链路，`CHAT` 如受共享抽象影响，仅做必要对齐
- 前端展示效果保持不变的前提是后端历史详情能够投影成与实时路径一致的契约；若契约已有冗余，可在后端内部收敛，但不要求前端改成另一套历史模式
