## Context

当前 `deep_search` 的查询分解和搜索结果数据已经具备：

- Python / Java 链路会稳定输出 `extend -> search -> report` 三个阶段。
- `extend` 阶段已经带有 `searchResult.query`，可直接拿到查询分解内容。
- 右侧工作区已经有 `SearchListRenderer`，可以把搜索结果以来源卡片形式展示出来。

但主对话区目前只有一条紧凑的工具行，最多显示“正在搜索 / 搜索完成 + 查询文本”，真正接近用户预期的搜索结果组件仍然只存在于右侧工作区。这造成两个问题：

1. 用户在主对话流里看不到完整的搜索中状态，只能看到一行摘要。
2. 查询分解内容虽然已经有了，但主要被引导到工作区查看，而不是直接出现在对话上下文里。

这次变更的核心不是新增协议或改 deep_search 算法，而是把现有搜索组件能力迁移到“对话区优先展示”的交互模型上。

## Goals / Non-Goals

**Goals:**

- 在对话区内联展示 deep_search 的搜索组件，而不是只显示一条任务摘要。
- `extend` 阶段复用“搜索完成”组件的视觉结构，显示查询分解内容、搜索中标题和加载动画。
- `search` 阶段沿用同一个组件容器，平滑切换为搜索完成并展示真实来源卡片。
- 保持 `report` 阶段仍以总结内容呈现，不把总结混进搜索中组件。
- 保证实时流式和历史回放都遵循相同的对话区渲染规则。

**Non-Goals:**

- 不修改 deep_search 后端协议、消息字段或搜索引擎执行逻辑。
- 不把右侧工作区做成这次变更的主交付目标；工作区可继续保留辅助查看能力，但不是验收重点。
- 不新增独立的深度搜索数据模型或数据库结构。
- 不重做整套对话视觉语言，仅在现有设计体系下复用搜索结果卡片样式。

## Decisions

### Decision 1: 让对话区成为 deep_search `extend/search` 的主展示面

采用方案：

- 在 `Dialogue` 渲染链路中，为 `deep_search` 的 `extend` 和 `search` 阶段增加专门的内联卡片视图。
- 右侧工作区继续作为附加查看入口，但用户不需要切换到工作区才能看到查询分解和搜索来源。

原因：

- 用户的预期是主对话流里就能看见“正在搜索什么”，而不是切到辅助面板。
- 对话区承载主要交互语境，更适合放阶段性搜索反馈。

备选方案：

- 方案 A：继续只在工作区展示卡片，对话区保留一行摘要。问题是无法满足“主对话区可见”的明确诉求。

### Decision 2: 抽离可复用的 deep_search 卡片，而不是直接把 `SearchListRenderer` 硬塞进 `Dialogue`

采用方案：

- 将当前右侧工作区依赖的搜索来源展示能力拆成对话区与工作区可共享的展示组件或共享渲染片段。
- 该组件接收统一的 deep_search 展示数据：阶段、标题、副标题、loading 状态、来源列表、空态文案。

原因：

- `SearchListRenderer` 目前默认假设“这是工作区详情面板”，直接复用会把布局、间距和语义耦死在工作区。
- 抽离共享展示层能减少重复样式和重复数据映射，同时保留对话区与工作区各自的容器差异。

备选方案：

- 方案 A：在 `Dialogue` 里复制一份卡片代码。问题是后续搜索完成态和搜索中态会出现双份维护。
- 方案 B：直接在对话区调用现有 `ActionPanel`。问题是会把工作区面板语义和交互带进聊天消息，不够干净。

### Decision 3: `extend` 阶段使用“待检索项”填充卡片，`search` 阶段用真实来源覆盖

采用方案：

- `extend` 阶段根据 `searchResult.query` 生成待检索项，组件视觉上沿用来源卡片列表，但卡片内容是查询分解文本，整体标题为“正在搜索”，并显示 loading 动画。
- `search` 阶段保留同一布局，用真实 `docs` 替换内容，并把标题切到“搜索完成”。

原因：

- 用户明确要求“就是现在搜索完成组件的那个效果，只是状态改成正在搜索”。
- 这样可以保证 `extend -> search` 是同一块 UI 的状态切换，而不是两个完全不同的组件。

备选方案：

- 方案 A：`extend` 阶段只显示纯文本列表。问题是与“搜索完成”阶段视觉割裂，且不符合用户要求。

### Decision 4: `report` 阶段继续回到总结渲染，不把总结内容堆进搜索卡片

采用方案：

- `extend/search` 用搜索状态组件。
- `report` 继续使用现有总结内容展示方式。

原因：

- 搜索过程组件的职责是展示“搜什么、搜到了什么”，总结阶段是另一种信息密度和版式，不适合塞进同一卡片。
- 这能保持组件职责单一，避免一个 deep_search 组件承担过多状态分支。

### Decision 5: 回放和实时流式共享同一份 deep_search 视图模型

采用方案：

- 在消息归一化或渲染辅助层生成统一的 deep_search 展示数据，供实时消息和历史回放共用。

原因：

- 当前历史回放已经能恢复 `extend/search/report` 阶段，差的是对话区渲染结果一致性。
- 统一视图模型可避免“实时时是卡片，回放时又退回摘要行”的不一致。

## Risks / Trade-offs

- [对话区卡片过重，导致消息流显得更长] → 仅对 `deep_search` 的 `extend/search` 启用卡片化展示，`report` 仍保持总结视图，避免整个对话区都被大卡片淹没。
- [工作区与对话区共用组件后出现样式耦合] → 抽离展示层与容器层，工作区和对话区分别包裹自己的布局。
- [`extend` 阶段没有真实 docs，卡片内容显得像“伪结果”] → 明确文案与 loading 状态，卡片内容标识为待检索查询项，而非搜索来源。
- [历史回放渲染与实时流式不一致] → 统一用归一化后的 deep_search 视图模型驱动两条链路，并补充对应测试。

## Migration Plan

1. 梳理 deep_search 当前在 `Dialogue`、`ActionPanel`、消息归一化中的数据流。
2. 抽离可复用的 deep_search 对话卡片展示组件或共享视图片段。
3. 在 `Dialogue` 中接管 `extend/search` 阶段渲染，让对话区直接显示搜索中/搜索完成组件。
4. 校验右侧工作区仍可正常查看 deep_search 详情，但不再作为本需求验收入口。
5. 补充实时流式与历史回放的验证后上线；如需回滚，只需恢复 `Dialogue` 中 deep_search 的紧凑摘要渲染逻辑。

## Open Questions

- `extend` 阶段的卡片项文案是否直接显示子查询原文，还是加前缀如“待检索：xxx”；本次默认保留原查询文本，避免信息噪音。
- 对话区的搜索中卡片是否需要显示“共 N 个搜索方向”之类的辅助计数；若现有标题与加载态已足够，可以先不加。
