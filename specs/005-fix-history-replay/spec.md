# Feature Specification: 对话细节统一 UI 与最终态历史重构

**Feature Branch**: `[005-fix-history-replay]`  
**Created**: 2026-04-16  
**Status**: Draft  
**Input**: User description: "把深度思考和深度研究的历史对话改成和进行中的对话同一套 UI。总体要求是：进行中的对话从后端接收数据渲染，历史对话也从后端获取数据渲染，两者入口与处理逻辑应保持一致，只是数据来源不同；若历史数据无法适配现有进行中对话的渲染逻辑，优先调整后端持久化与历史详情数据格式，而不是继续保留历史专用 UI。"

## Existing System Context *(mandatory for brownfield features)*

- **Affected Modules**: `ui`、`ai-agent-station-study-domain`、`ai-agent-station-study-trigger`、`ai-agent-station-study-app`
- **Existing Capabilities to Reuse**: 当前进行中对话的细节展示体验、现有流式对话数据接入链路、现有历史列表与详情接口、现有工作区预览面板、现有稳定文件引用能力
- **Out of Scope**: 不新增第三套历史专用界面、不恢复逐 token 或逐增量实时回放、不重做普通 `CHAT` 的轻量聊天模式、不改造无关的数据分析主流程、不为旧错误历史数据提供长期兼容方案
- **Current Constraints**: 当前进行中对话与历史对话仍走两套细节展示路径，导致视觉结构、卡片类型、点击行为和最终状态恢复不一致；本次必须把深度思考与深度研究统一到同一套对话细节 UI 上，并以当前进行中对话布局作为唯一基线，优先让历史去适配它，而不是反向重做进行中体验；如果现有历史数据形状无法复用该链路，必须优先调整后端持久化语义与详情返回结构，使历史数据能够直接服务于统一 UI

## Clarifications

### Session 2026-04-16

- Q: 历史与进行中的关系应该如何定义？ → A: 两者应视为同一套对话细节体验的不同数据来源，入口和处理逻辑应保持一致，不能继续保留历史专用 UI
- Q: 这次统一 UI 的正式适用范围是什么？ → A: 覆盖 `PLAN_SOLVE`（深度思考）与 `REACT`（深度研究）；普通 `CHAT` 继续保持轻量模式
- Q: 如果历史数据无法直接喂给现有进行中对话的展示链路，应优先改哪里？ → A: 优先改后端持久化语义和历史详情返回格式，使历史数据适配统一展示模型，而不是再做一套历史专用渲染逻辑
- Q: 历史是否还要回放全部执行过程增量？ → A: 不需要逐增量回放，但凡在对话结束时界面上仍可见的细节块，都必须通过统一 UI 原样复现
- Q: 统一 UI 后的验收基准是什么？ → A: 用户在对话结束时看到的那份进行中对话界面，就是几天后重新打开历史时必须复现的同一份界面
- Q: 统一界面基线应如何定义？ → A: 以当前进行中对话的现有布局作为唯一基线；历史必须 1:1 适配它
- Q: 统一范围是否包含工作区面板？ → A: 左侧对话区和右侧工作区入口、计划入口、产物预览都必须统一
- Q: 历史详情与进行中数据在进入前端前应如何对齐？ → A: 两者都必须产出同一份 canonical detail contract，并走同一套前端处理路径
- Q: 哪些终态轮次必须通过统一 UI 复现最后界面？ → A: 只要该轮已结束，无论是 completed、error 还是 force_stop，都必须展示最后可见细节和对应终态状态
- Q: 最终可见细节块应按什么粒度持久化？ → A: 每个最终仍可见的细节块都必须独立持久化为一条明细记录，并带稳定 block identity、display order、final status 与 payload snapshot

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 历史重开与进行中使用同一套细节界面 (Priority: P1)

作为查看深度思考或深度研究结果的用户，我希望对话进行中看到的细节界面和之后重开历史时看到的是同一套界面结构、同一类卡片和同一组交互入口，而不是进行中与历史分别使用两套不同 UI。

**Why this priority**: 这是本次需求的核心。如果历史仍然是另一套界面，就算内容接近，用户也会认为历史和真实对话体验不一致，无法建立稳定预期。

**Independent Test**: 完成一条 `PLAN_SOLVE` 或 `REACT` 会话，记录对话结束时界面的细节结构、卡片顺序、标题和可点击入口；刷新页面或数天后重开同一会话，确认历史展示仍使用同一套界面结构和相同交互入口。

**Acceptance Scenarios**:

1. **Given** 一条深度思考会话在结束时展示了思考区、计划区、任务分组、工具卡片和结果区，**When** 用户刷新页面并重开该会话，**Then** 历史详情必须继续以同一套界面结构展示这些内容，而不是切换到另一种历史专用布局
2. **Given** 一条深度研究会话在结束时展示了搜索、总结和结果卡片，**When** 用户延迟重新打开该会话，**Then** 历史详情必须复现与结束时一致的卡片类型、排列顺序和主要交互入口

---

### User Story 2 - 最终状态通过统一界面稳定复现 (Priority: P2)

作为回看已完成对话的用户，我希望计划完成态、思考文本、工具调用状态、搜索结果和总结卡片在历史中仍以结束时的最终状态出现在同一套界面上，而不是因为切换到历史模式而回退、折叠或替换成摘要。

**Why this priority**: 即便 UI 结构统一，如果最终状态不能稳定复现，用户仍然无法依赖历史来还原当时的真实执行过程和结果。

**Independent Test**: 完成一条含多步骤计划、多个工具细节和搜索/总结卡片的结构化会话；记录其结束时的状态与顺序；重开历史后验证相同界面上的最终状态未回退、未折叠、未被摘要替代。

**Acceptance Scenarios**:

1. **Given** 一条深度思考会话的多个计划步骤在结束时已显示为完成，**When** 用户重开历史，**Then** 这些步骤必须继续在同一计划界面中显示为完成，而不是退回初始状态或只剩单条摘要
2. **Given** 一条结构化会话在结束时保留了多个同类型工具卡片和思考文本块，**When** 用户重开历史，**Then** 统一界面中必须继续显示相同数量和顺序的最终细节块，不能只保留第一条或压缩成“完成”提示
3. **Given** 一条结构化会话以错误或强制停止结束，且结束前界面上已经显示了部分思考、计划或工具细节，**When** 用户重开历史，**Then** 统一界面必须继续展示这些最后可见细节，并明确标注该轮的终态，而不是退化成空白或简化摘要

---

### User Story 3 - 工作区与详情入口在统一界面中保持一致 (Priority: P3)

作为复用历史成果的用户，我希望在进行中对话和历史对话中都能通过同样的入口查看工作区文件、HTML/Markdown 报告、计划详情或其他最终产物；当资源失效时，也希望在这套统一界面中看到明确原因，而不是出现历史专用的通用错误。

**Why this priority**: 统一 UI 不仅是视觉一致，还包括点击入口和结果预览体验一致。否则用户仍然需要区分“现在的对话”和“历史的对话”。

**Independent Test**: 完成一条会生成文件或报告的会话；记录结束时点击入口和预览结果；重开历史后通过同样入口再次查看，确认预览正常或看到明确缺失原因。

**Acceptance Scenarios**:

1. **Given** 一条已完成会话在结束时可通过对话细节区或工作区入口查看最终产物，**When** 用户重开历史并点击同一类入口，**Then** 系统必须在统一界面中展示同类预览结果
2. **Given** 某个历史产物引用已经失效，**When** 用户通过统一界面点击该产物，**Then** 系统必须显示明确不可用原因，而不是显示泛化的加载失败提示

---

### Edge Cases

- 用户在会话刚结束或页面刷新后立即重新进入时，系统仍必须使用统一界面展示当前可用的最终细节，而不是因为状态切换暂时落回另一套布局
- 同一轮对话中存在多个同类型搜索或工具细节时，统一界面在历史模式下仍必须逐条展示，不能因为数据恢复而只剩第一条
- 若某些思考或工具细节在执行过程中出现过，但在结束前已从界面消失，则历史不要求回放这些瞬时内容
- 若某个细节块在结束时同时关联对话区与工作区，历史仍必须通过统一界面恢复这两处关系，而不能出现两份互相漂移的副本
- 当历史数据尚未能直接复用统一界面输入模型时，系统必须优先修正历史数据形状，而不是新增一条历史专用展示分支
- 普通 `CHAT` 模式不应因为本次结构化统一而被强行改造成复杂的多区块对话界面

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 以当前进行中对话的现有布局作为 `PLAN_SOLVE` 与 `REACT` 的唯一对话细节界面基线，使进行中对话与历史重开都复用同一种可见结构与交互方式
- **FR-002**: 系统 MUST 在历史重开时复现与对话结束时相同的细节块集合，包括思考文本、计划、任务分组、工具调用、搜索/总结卡片、最终答案和最终产物入口
- **FR-003**: 系统 MUST 让“进行中”和“历史”之间的主要区别仅体现在数据来源，而不是界面结构、卡片类型、入口位置或交互逻辑
- **FR-004**: 系统 MUST 让进行中数据与历史详情数据在进入前端前都收敛为同一份 canonical detail contract，并复用同一套前端处理路径
- **FR-005**: 系统 MUST 让历史详情数据能够直接服务于统一对话细节界面，而不是依赖历史专用的二次推理、摘要补丁、单独 normalization 分支或替代布局
- **FR-005A**: 若现有历史数据形状无法直接支持统一界面，系统 MUST 优先调整持久化语义与历史详情返回结构，使其产出 canonical detail contract，而不是继续保留历史专用渲染路径
- **FR-006**: 系统 MUST 保留对话结束时仍可见的完整思考文本，并在历史中通过统一界面继续展示该文本，而不是退化成“思考完成”等占位提示
- **FR-007**: 系统 MUST 保留对话结束时仍可见的计划步骤最终状态，并在历史中通过同一计划界面继续展示这些最终状态
- **FR-008**: 系统 MUST 保留对话结束时仍可见的工具调用、搜索和总结细节，并在历史中通过相同类型的卡片继续展示其标题、状态和用户可读摘要
- **FR-008A**: 系统 MUST 将 `completed`、`error` 与 `force_stop` 视为统一界面必须支持的已结束终态，并在历史中同时恢复最后可见细节与对应终态标识
- **FR-009**: 系统 MUST 支持同一轮对话保留多个同类型最终细节块，只要这些块在对话结束时可见，统一界面在历史模式下也必须逐条展示
- **FR-010**: 系统 MUST 保持进行中与历史中的点击入口语义一致，使用户在两种场景下都能通过同类入口查看计划详情、工具结果和工作区产物
- **FR-010A**: 系统 MUST 将左侧对话区与右侧工作区相关入口都纳入统一范围，不允许只统一对话区而保留另一套历史专用工作区体验
- **FR-011**: 系统 MUST 为同一份同时出现在对话区和工作区的最终细节维护单一 canonical 记录，并恢复其跨区域展示关系，避免出现两份不同真相源
- **FR-012**: 系统 MUST 让历史详情存在单一持久化真相源，避免读取历史时再从少量摘要事件推导出另一套替代视图
- **FR-013**: 系统 MUST 继续将会话列表所需的轻量摘要信息与会话详情所需的统一细节数据分离，避免为列表读取携带不必要的详细载荷
- **FR-014**: 系统 MUST 让会话级存储只承担会话归属、标题、模式、排序、预览和计数等轻量摘要职责
- **FR-015**: 系统 MUST 让单轮级存储只承担最终答案、执行状态、基础指标和必要摘要职责
- **FR-016**: 系统 MUST 让细节级存储承担统一细节界面的最终可见细节记录职责，且一条记录对应一个最终界面可见细节单元
- **FR-016A**: 系统 MUST 为每个最终仍可见的细节块独立持久化 stable block identity、display order、final status 与 payload snapshot，禁止将多个最终可见同类块合并后再依赖读取期拆分
- **FR-017**: 系统 MUST 通过稳定且长期可解析的引用恢复历史工作区产物，使统一界面中的产物预览不依赖临时路径或运行时上下文
- **FR-018**: 系统 MUST 在历史产物无法访问时，通过统一界面返回明确不可用状态和原因，而不是通用加载失败提示
- **FR-019**: 系统 MUST 将统一对话细节模型正式应用到 `PLAN_SOLVE` 与 `REACT`，并保持两者在历史与进行中之间的展示体验一致
- **FR-019A**: 系统 MUST 保持普通 `CHAT` 继续使用轻量历史与轻量对话体验，不因本次结构化统一而被强制迁移到同一套复杂细节模型
- **FR-020**: 系统 MUST 支持对“对话结束时的进行中界面”和“重开后的历史界面”做 1:1 对照验收，以验证统一界面与最终状态一致性
- **FR-021**: 系统 MUST 使新的历史持久化模型围绕“统一界面可长期复看”的目标演进，而不是再次围绕完整实时回放能力堆叠冗余结构
- **FR-022**: 系统 MUST 不要求为旧错误历史模型提供长期双路径兼容；如有必要，可在切换前直接清理旧数据

### Key Entities *(include if feature involves data)*

- **Canonical Conversation Detail View**: 深度思考与深度研究共用的对话细节界面基线，定义用户在进行中和历史中看到的同一组结构、卡片和入口
- **Canonical Detail Contract**: 统一对话细节界面的标准输入模型，进行中数据与历史详情数据都必须先收敛到该契约后再进入前端处理链路
- **Live Detail Feed**: 进行中对话的数据来源，持续产出符合 canonical detail contract 的当前阶段可见细节内容
- **Historical Detail Feed**: 历史重开时的数据来源，产出符合 canonical detail contract 的对话结束时最终仍可见细节内容
- **Final Visible Detail Block**: 对话结束时界面上最终仍可见的单个细节单元，例如思考文本、计划状态、工具卡片、搜索卡片、总结卡片或产物入口
- **Detail Block Snapshot**: 某个最终可见细节块在轮次结束时的持久化快照，包含稳定身份、显示顺序、终态信息与用于历史复现的展示载荷
- **Conversation Turn**: 一轮用户请求及其完成结果，是统一细节数据的父级单元
- **Workspace Artifact Reference**: 指向历史工作区结果内容的稳定引用，用于在统一界面中再次预览最终产物

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在验收样本中，100% 的 `PLAN_SOLVE` 与 `REACT` 会话在重开历史后继续使用与结束时相同的细节界面结构，不再出现历史专用替代布局
- **SC-002**: 在验收样本中，100% 对话结束时仍可见的思考、计划、工具、搜索和总结细节块，在历史重开后保持相同的数量、顺序和主要文案
- **SC-003**: 在验收样本中，100% 已完成的计划步骤在历史重开后仍显示为完成状态，不回退为初始状态或摘要态
- **SC-004**: 对于结束时含多个同类型细节块的会话，100% 的样本在历史重开后保留相同数量的同类细节块，不发生错误折叠
- **SC-005**: 对包含工作区文件或报告的会话，95% 以上的历史产物入口在首次点击时能成功预览；其余情况必须展示明确不可用原因
- **SC-006**: 在验收样本中，用户通过统一界面访问计划详情、工具结果和工作区产物时，进行中与历史两种场景的入口位置和交互结果保持一致
- **SC-007**: 在验收样本中，100% 已结束但非成功完成的结构化会话在历史重开后仍能展示其最后可见细节，并明确展示 `error` 或 `force_stop` 终态

## Assumptions

- 当前进行中对话的细节展示体验是本次统一 UI 的基线，历史体验需要向它收敛，而不是反过来
- 当前进行中对话的现有布局在本次范围内应尽量保持稳定，历史需要 1:1 适配它，而不是推动进行中界面大改
- 右侧工作区、计划入口和产物预览同样属于本次统一范围，不能作为历史专用例外路径保留
- `PLAN_SOLVE` 与 `REACT` 都需要结构化细节界面，因此两者都在本次统一范围内
- 普通 `CHAT` 在本次范围内继续保持轻量模式，不作为统一结构化细节界面的首要目标
- 如现有历史事件载荷无法直接满足统一界面输入要求，可通过调整持久化语义与详情返回结构解决，而不是新增历史专用前端分支
- 进行中数据与历史详情数据都应先收敛为同一份 canonical detail contract，再进入统一前端处理链路
- 旧历史数据若与新模型不兼容，可在切换前清理，不以兼容旧错误数据为本次验收目标
- 本次仍不要求历史逐 token 或逐增量回放，只要求长期稳定复现对话结束时最终仍可见的细节界面
- 只要某轮已进入终态，无论成功、错误还是强制停止，历史都必须复现该轮结束时最后可见的统一界面
- 细节级持久化应以“一个最终可见块一条记录”为默认粒度，避免读取历史时再把合并载荷反向拆分
