# Feature Specification: 对话历史持久化精简重构

**Feature Branch**: `[004-conversation-history-refactor]`  
**Created**: 2026-04-12  
**Status**: Draft  
**Input**: User description: "重构 React 和 PlanAndSolve 对话历史持久化与回显逻辑，精简重复字段和表结构设计，提升可维护性与扩展性"

## Existing System Context *(mandatory for brownfield features)*

- **Affected Modules**: `ui`、`ai-agent-station-study-domain`、`ai-agent-station-study-trigger`、`ai-agent-station-study-app`
- **Existing Capabilities to Reuse**: 现有 `AgentStreamPersistServiceImpl` 流式累积逻辑、`OrderedEvent` 事件模型、会话列表/详情接口、`render_snapshot_json` 回放兼容能力、前端 `restoreMessages` 与 `handleTaskData` 回放转换逻辑
- **Out of Scope**: 不改动上游 Agent SSE 协议、不重做 chat 角色绑定规则、不落地二期 artifact/workspace 精确恢复能力、不扩展无关业务模块
- **Current Constraints**: 必须保持历史消息可读、保持现有深度思考与深度研究可回显、遵守 DDD 分层边界、兼容匿名设备会话与用户迁移能力、避免影响现有流式交互体验

## Clarifications

### Session 2026-04-12

- Q: 单一权威的持久化回放表示应以什么为准？ → A: 事件流是唯一权威；消息表只保留单次请求相关信息，不存会话细节；新增前端展示内容应通过事件载荷扩展而非修改表结构
- Q: 工作区搜索总结内容应如何持久化？ → A: 事件中只保存路径或引用，不直接保存总结正文
- Q: 路径或引用应指向哪类资源？ → A: 指向稳定的持久化资源标识，不依赖当前工作区或本机临时路径
- Q: 旧历史数据采用什么兼容迁移策略？ → A: 不保留旧历史数据兼容；旧数据允许在上线前直接删除，本次重构仅覆盖新写入数据

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 稳定回放历史对话 (Priority: P1)

作为回访用户，我希望在刷新页面或切换历史会话后，依然能看到完整的深度思考或深度研究过程，而不是因为持久化字段重复、回放链路分叉而出现缺失、错序或展示不一致。

**Why this priority**: 这是本次重构的核心价值。用户真正关心的是历史消息能否稳定回显，若这一点不成立，后续数据结构优化没有意义。

**Independent Test**: 分别发送一条 `PLAN_SOLVE` 和一条 `REACT` 消息，等待完成后刷新页面并重新打开历史会话，应能看到与原始执行结果一致的时间线和最终结论。

**Acceptance Scenarios**:

1. **Given** 已完成的深度思考会话包含多段思考、任务和结论，**When** 用户刷新页面后重新打开该会话，**Then** 系统应按原始顺序回放关键步骤并展示最终答案
2. **Given** 已完成的深度研究会话包含搜索、工具调用和总结，**When** 用户查看历史详情，**Then** 前端应能直接使用单一权威回放数据完成渲染，而不是再从多份重叠字段进行拼装
3. **Given** 系统切换到新持久化模型并清理旧历史数据，**When** 用户查看历史会话，**Then** 页面只需保证新模型写入的会话可正常回放，不承担旧模型数据兼容义务

---

### User Story 2 - 简化前端历史状态 (Priority: P2)

作为前端开发者，我希望历史会话以服务端数据为唯一持久化真相源，本地只保留草稿和流式中的临时状态，这样切换、新建、删除和懒加载详情时就不需要维护两套重复的会话元数据。

**Why this priority**: 当前前端同时维护 `remoteConversations`、`conversations`、草稿会话和已加载详情，状态合并规则复杂，是回显逻辑臃肿的重要来源。

**Independent Test**: 在保留“新建空白对话”“切换历史会话”“懒加载详情”“删除当前对话”这些能力的前提下，验证前端无需手工合并两份持久化元数据也能完成同样的交互。

**Acceptance Scenarios**:

1. **Given** 用户存在远端历史会话且当前页面有一个未发送的草稿会话，**When** 历史列表刷新，**Then** 服务端历史与本地草稿应分别按职责存在，不应互相覆盖或重复映射
2. **Given** 用户首次打开一个尚未加载详情的历史会话，**When** 前端请求详情成功，**Then** 页面应只补充该会话所需的详情缓存，而不是重建整份会话列表状态
3. **Given** 当前会话已经有持久化消息，**When** 用户切换角色或新建对话，**Then** 系统应生成新的草稿上下文而不污染既有历史会话元数据

---

### User Story 3 - 优雅演进持久化模型 (Priority: P3)

作为后端开发者和数据库维护者，我希望对话持久化模型能够用更少的重复字段表达同样的业务语义，使后续新增回放节点、扩展模式或优化接口时不再反复堆积 nullable 字段和冗余关联键。

**Why this priority**: 当前三张表和详情接口同时保存摘要、快照、事件、聚合 JSON 与多份冗余 ID，后续每次扩展都会继续放大复杂度。

**Independent Test**: 用一套重构后的数据模型承载 `CHAT / PLAN_SOLVE / REACT` 三类消息，并验证新增回放节点类型时只需扩展单一权威载荷与对应映射规则。

**Acceptance Scenarios**:

1. **Given** 一条新完成的 `PLAN_SOLVE` 或 `REACT` 消息，**When** 系统持久化该轮对话，**Then** 回放所需核心内容应落在单一权威消息载荷中，而不是分散到多份语义重叠的字段
2. **Given** 一条回放事件从属于某条消息，**When** 系统保存事件记录，**Then** 事件应以消息为父级上下文，只有确有查询或约束价值的关联字段才允许保留为冗余列
3. **Given** 会话列表只需要展示摘要信息，**When** 用户打开历史侧栏，**Then** 系统不应为每个会话传输完整回放明细

### Edge Cases

- 会话已创建但尚未产生任何消息时，列表和详情都必须保持轻量，不应生成无意义的回放载荷
- 上游流式执行中途中断、报错或被强制停止时，系统仍需保留当时已经完成的历史片段与状态信息
- 同一会话在刷新列表、切换详情和本地草稿存在的情况下，不应因为多份状态源造成重复项或选中项丢失
- `CHAT` 模式虽然不是本次重构主目标，但共享抽象变化不能破坏现有 chat 上下文滑动窗口和角色绑定行为
- 工作区搜索或总结节点若只保存路径/引用，则当引用目标丢失、过期或不可访问时，历史详情必须能明确告知用户该内容不可读取，而不是静默失败
- 工作区或本机临时目录被清理、迁移或重建后，历史会话中的引用内容仍必须可按持久化资源标识重新定位或明确报错
- 上线切换前若执行旧历史数据删除，删除动作必须发生在启用新模型之前，并避免让前端继续请求已失效的旧会话

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 为每一轮 `PLAN_SOLVE` 与 `REACT` 消息定义以事件流为唯一权威的持久化回放表示，历史详情与回显优先从事件流装配，而不是从多份语义重叠字段中重新拼装
- **FR-002**: 系统 MUST 将会话级存储限制为列表与归属所需的轻量摘要信息，包括身份、标题、模式、排序、预览、置顶和计数等元数据
- **FR-003**: 系统 MUST 继续以“单轮消息”为边界保存一次用户输入与对应执行结果，但消息实体只保留该次请求的身份、输入、状态、附件、基础指标和必要派生摘要，不再存储会话细节型回放内容
- **FR-004**: 系统 MUST 为回放事件定义清晰的父子关系，事件默认从属于消息实体，并承载思考过程、工具调用结果、搜索过程、总结内容等会话细节；只有在查询性能、唯一约束或兼容迁移确有必要时才允许保留冗余标识
- **FR-005**: 系统 MUST 为 `CHAT / PLAN_SOLVE / REACT` 提供统一但可扩展的事件载荷抽象，使新增前端展示节点时优先通过事件内容扩展完成，而不是持续新增仅对单一模式生效的表字段
- **FR-006**: 系统 MUST 对工作区搜索结果、总结报告等大体量展示内容采用引用式持久化，事件中仅保存路径或引用标识，不直接长期保存完整正文
- **FR-007**: 系统 MUST 让此类引用指向稳定的持久化资源标识，而不是当前工作区路径、本机临时文件路径或依赖单次运行上下文的地址
- **FR-008**: 系统 MUST 保障流式执行结束后的历史回放语义与用户实时看到的最终结果一致，包括最终答案、关键思考文本、主要任务推进和工具/搜索里程碑
- **FR-009**: 系统 MUST 不再为改造前旧历史数据提供长期兼容读取能力，允许在上线切换前直接删除旧数据，本次重构仅保证新模型写入数据可读
- **FR-010**: 系统 MUST 让前端将服务端会话列表视为已持久化历史的唯一真相源，本地状态仅保留草稿输入、流式进行中状态和已加载详情缓存
- **FR-011**: 系统 MUST 让前端历史详情加载只补充当前选中会话的回放数据，不再维护一套与服务端列表等价的重复元数据副本
- **FR-012**: 系统 MUST 在现有模块边界内明确职责归属：`ai-agent-station-study-domain` 负责消息聚合与回放装配，`ai-agent-station-study-trigger` 负责历史查询契约，`ui` 负责草稿与详情缓存分层，`ai-agent-station-study-app` 负责表结构与 Mapper 落地
- **FR-013**: 系统 MUST 明确本次重构涉及的数据契约变化，说明哪些现有字段被删除、转为派生字段或完全下线，哪些字段仍作为列表摘要长期保留
- **FR-014**: 系统 MUST 让会话列表接口只返回历史列表展示所需数据，详情接口只返回回放与渲染真正需要的数据，避免一次查询携带重复或不会被消费的历史载荷
- **FR-015**: 系统 MUST 在引用式内容不可读取时返回明确的可展示错误状态或缺失状态，使前端能够向用户说明内容缺失原因

### Key Entities *(include if feature involves data)*

- **Conversation Summary**: 面向历史列表的轻量会话摘要，包含会话身份、归属、标题、模式、排序时间、预览文本、置顶状态、消息轮数和角色快照
- **Conversation Turn**: 一轮用户输入及其对应 Agent 执行结果的聚合单元，包含请求身份、输入内容、执行状态、附件信息、基础指标和必要派生摘要，但不承载完整会话细节
- **Replay Event**: 从属于某条 `Conversation Turn` 的有序历史节点，是历史回放的唯一权威来源，用于表达思考、计划、任务、搜索、工具结果和结论等阶段性里程碑，并为未来新增展示节点预留扩展空间
- **Referenced Workspace Artifact**: 由工作区搜索、总结或报告节点引用的稳定持久化内容载体，使用文件服务 ID、对象存储 key、稳定下载地址等长期可解析标识，不依赖当前工作区临时路径
- **Draft Conversation Cache**: 仅存在于前端运行时的草稿与流式缓存，用于承接未持久化输入和当前打开详情，不承担持久化真相源职责

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在验收样本中，100% 的已完成 `PLAN_SOLVE` 与 `REACT` 会话在页面刷新后都能重新打开，并按正确顺序展示关键历史节点与最终结论
- **SC-002**: 历史侧栏在加载最近 50 条会话时，仅依赖轻量摘要数据即可完成首屏展示，用户在 1 秒内可以开始选择会话
- **SC-003**: 对新模型验收样本，历史回放的最终答案、关键里程碑顺序和会话标题/预览结果保持一致，不因字段精简出现可见回归
- **SC-004**: 每条新写入的 `PLAN_SOLVE` 与 `REACT` 消息都只存在一份事件流权威回放来源，消息表不再额外长期保存同语义的会话细节字段作为主要读取来源
- **SC-005**: 前端在“新建草稿、切换会话、懒加载详情、删除当前会话、刷新页面”五类核心场景下，不再需要手工合并两套持久化会话元数据即可完成交互
- **SC-006**: 对大体量工作区总结或搜索结果，历史持久化不再因为正文变长而要求新增表字段；新增展示类型时可通过新增事件引用类型完成扩展
- **SC-007**: 清理工作区临时文件或切换部署实例后，历史会话中基于引用的工作区内容仍可通过持久化资源标识继续访问，或返回明确缺失状态

## Assumptions

- 本次重构聚焦 `PLAN_SOLVE` 和 `REACT` 历史持久化与回显，`CHAT` 只在共享抽象层面做必要对齐，不主动改变既有业务体验
- 现有上游 SSE 事件协议、`OrderedEvent` 基础语义和实时渲染交互保持不变，重构重点在落库模型与历史读取链路
- 匿名设备标识、会话迁移到用户账号的规则继续沿用现有能力，不在本需求内重设计权限模型
- 改造前旧历史数据不纳入保留范围，可在上线切换前直接清理
- 前端允许继续保留运行时草稿和进行中消息缓存，但这些缓存不应再承担已持久化历史元数据的长期存储职责
- 会话级摘要与消息级派生缓存可以保留少量加速查询字段，但这些字段不能再成为历史回放的主读取依据
- 被事件引用的工作区内容存在独立存储位置，并且允许前端在历史查看时按需读取
- 持久化资源标识的生命周期长于单次会话执行过程，能够满足历史会话回看需要
