# Feature Specification: Conversation History Replay

**Feature Branch**: `[017-conversation-history-projector-replay]`  
**Created**: 2026-05-02  
**Status**: Draft  
**Input**: User description: "`docs/superpowers/plans/2026-05-01-conversation-history-projector-replay.md`"

## Existing System Context *(mandatory for brownfield features)*

- **Affected Modules**: `ai-agent-station-study-domain`、`ai-agent-station-study-trigger`、`ai-agent-station-study-app`、`ui`
- **Existing Capabilities to Reuse**: 现有会话执行账本、历史投影与工具结果回放能力、现有会话列表与流式对话展示链路、现有稳定产物引用能力
- **Out of Scope**: 不重做普通 `CHAT` 轻量对话模式、不按设备或归属人自动推断默认会话、不改造 `reactor-tool/` 与 `reactor-client/`、不重做完整历史侧边栏体验
- **Current Constraints**: 历史重放必须与进行中对话细节保持一致；当前版本只按明确的 `sessionId` 恢复会话；失败、中断与缺失产物场景都需要可读回显；新能力必须复用现有账本与回放抽象，不能形成并行真相源

## Clarifications

### Session 2026-05-02

- Q: 本期会话列表的可见范围是什么？ → A: 终端用户可查看系统内所有近期会话
- Q: 系统范围会话列表里，默认展示多少条近期会话？ → A: 20 条
- Q: 当前 `sessionId` 自动恢复失败时，前端默认应该怎么处理？ → A: 保持当前空白或初始界面，并提示用户从近期会话列表手动选择

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 刷新后恢复当前会话 (Priority: P1)

作为重新进入对话的用户，我希望在刷新页面或稍后重进时，系统能基于当前 `sessionId` 恢复完整的会话轨迹，这样我不需要重新询问或手动拼接之前已经完成的多轮结果。

**Why this priority**: 能否按会话恢复完整历史，是本次需求的核心价值；如果恢复链路不稳定，后续统计、列表和统一展示都没有意义。

**Independent Test**: 准备一个包含多轮请求的已完成会话；刷新页面或重新进入后，只提供原始 `sessionId`，确认系统能恢复全部已保存轮次、顺序和最终结论。

**Acceptance Scenarios**:

1. **Given** 一个会话中已经完成了多轮请求，**When** 用户使用同一个 `sessionId` 刷新页面并重新进入，**Then** 系统必须按原始顺序恢复该会话下所有已保存轮次
2. **Given** 某一轮对话没有显式的最终回答块，但已经有明确的轮次总结，**When** 用户重新打开历史，**Then** 系统必须仍然为该轮展示清晰的最终结论
3. **Given** 当前 `sessionId` 还没有可恢复历史，**When** 页面初始化，**Then** 系统必须保留当前空白或初始上下文，并提示用户从近期会话列表手动选择，而不是自动切换到其他无关会话

---

### User Story 2 - 历史与进行中保持同一套细节体验 (Priority: P2)

作为查看历史详情的用户，我希望历史会话与进行中的会话使用同一套可见细节结构，包括思考、任务推进、工具结果、总结和最终答案，这样我重新打开历史时看到的就是当时结束时的那份界面，而不是另一套历史专用视图。

**Why this priority**: 用户感知到的不是“账本是否存在”，而是“重开后看到的是否还是同一场对话”。如果历史和实时展示结构不一致，恢复能力就不算闭环。

**Independent Test**: 选取一条已结束的结构化会话，对比结束瞬间的界面与历史重开后的界面，确认主要细节块类型、顺序和终态一致。

**Acceptance Scenarios**:

1. **Given** 一条结构化会话在结束时展示了思考、任务、工具结果和最终答案，**When** 用户重新打开该会话，**Then** 历史详情必须继续按同样的细节类别和顺序展示这些内容
2. **Given** 一条会话在部分细节可见后以失败或强制停止结束，**When** 用户查看历史详情，**Then** 系统必须保留这些最后可见细节，并明确展示该轮的最终状态
3. **Given** 一条历史会话包含文件、报告或其他稳定引用内容，**When** 用户从历史详情进入对应入口，**Then** 系统必须展示同类结果，或在无法读取时给出明确不可用原因

---

### User Story 3 - 会话摘要与会话详情保持一致 (Priority: P3)

作为需要浏览近期对话的用户，我希望系统既能提供系统范围内的轻量会话摘要列表，也能在进入详情后展示对应会话的完整多轮内容，并保证两者看到的轮次数、最新状态和最近活动信息一致。

**Why this priority**: 只恢复详情而没有稳定的会话摘要，用户仍然难以定位要看的会话；但如果摘要与详情不一致，用户会失去对历史数据的信任。

**Independent Test**: 准备多个状态不同的会话，查看会话摘要列表，再逐个进入详情，确认标题、最近活动、轮次统计和最终状态保持一致。

**Acceptance Scenarios**:

1. **Given** 系统内存在多个近期会话，**When** 系统返回默认的会话摘要列表，**Then** 系统必须按最近活动时间倒序返回最近 20 条会话，且每个会话都包含足以区分与排序的摘要信息，包括标题、最近一次查询预览、最近活动和轮次结果概览
2. **Given** 一个会话下包含多轮请求，**When** 用户进入该会话详情，**Then** 系统必须将这些轮次作为同一会话的一部分完整展示出来
3. **Given** 某个会话的最近一轮改变了会话状态或最近活动时间，**When** 用户查看摘要列表和详情，**Then** 两处看到的最新状态与最近活动信息必须一致

### Edge Cases

- 当某轮对话缺少显式最终回答块时，系统必须使用该轮已有的最终总结保证用户仍能看到清晰结论
- 当会话以失败或强制停止结束时，系统必须保留结束前最后可见的细节块，而不是只显示空白结果
- 当历史引用的文件、报告或产物已经不可读取时，系统必须返回明确的不可用状态，而不是静默丢失内容
- 当同一会话存在多轮请求时，系统必须保持轮次顺序稳定，不能因为恢复路径变化而重排
- 当当前 `sessionId` 没有可恢复历史时，系统不得自动切换到其他会话，避免误展示无关内容

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST 为每个会话维护稳定的会话级标识与摘要，使同一会话能够被独立定位、恢复和排序
- **FR-002**: System MUST 将会话中的每一次用户请求视为独立轮次，同时保留其与所属会话的关联关系
- **FR-003**: System MUST 支持按 `sessionId` 读取历史，并按原始时间顺序恢复该会话下所有已保存轮次
- **FR-004**: System MUST 在历史重开时恢复每一轮结束时仍可见的关键细节块，包括思考、任务推进、工具或搜索结果、总结和最终结论
- **FR-005**: System MUST 为每一轮提供明确的最终结果；当缺少显式最终回答块时，必须使用该轮已有总结补足最终结论
- **FR-006**: System MUST 提供会话级摘要信息，包括标题、当前状态、最近请求、最近活动时间以及轮次结果统计
- **FR-006A**: System MUST 允许终端用户查看系统内所有近期会话的摘要列表，而不是仅限当前 `sessionId` 对应会话
- **FR-006B**: System MUST 将近期会话摘要列表的默认返回数量限定为最近 20 条，同时保持详情内容按需读取
- **FR-006C**: System MUST 按最近活动时间倒序返回近期会话摘要列表
- **FR-006D**: System MUST 在会话摘要列表中展示标题与最近一次查询预览，但不在未打开详情前展示该会话的总结内容
- **FR-007**: System MUST 明确由既有会话账本查询能力、历史投影能力和对话详情渲染链路共同承接本能力，而不是创建新的并行真相源或独立历史展示模型
- **FR-008**: System MUST 将会话摘要契约与会话详情契约分离，使列表读取保持轻量，而详情读取能提供完整回放内容
- **FR-009**: System MUST 让现有对话细节展示链路能够直接消费历史回放结果，而不要求新增历史专用界面结构
- **FR-010**: System MUST 对成功、失败和强制停止的轮次都保留可读历史，至少包括最后可见细节和最终状态标识
- **FR-011**: System MUST 在历史重开时继续使用稳定的产物引用；当引用不可读取时，必须返回明确的不可用状态
- **FR-012**: System MUST 将首页自动恢复范围限定在当前 `sessionId`；如果该会话没有历史，则不得自动切换到其他会话，但用户仍可从近期会话列表手动进入其他会话
- **FR-012A**: System MUST 在当前 `sessionId` 自动恢复失败时保留当前空白或初始界面，并提供用户从近期会话列表手动选择其他会话的明确入口
- **FR-013**: System MUST 在现有 `domain`、`trigger`、`app` 与 `ui` 模块边界内完成本能力，保持会话聚合、历史查询和前端恢复职责清晰
- **FR-014**: System MUST 保证会话摘要与会话详情看到的轮次数、最近活动和最终状态保持一致

### Key Entities *(include if feature involves data)*

- **Conversation Session**: 一条会话级记录，表示用户持续对话的容器，承载标题、状态、最近活动和轮次统计等摘要信息
- **Dialogue Run**: 会话中的一次独立请求及其完成结果，是历史恢复时的最小业务轮次单元
- **Replay Frame**: 用于重建历史详情的标准化事件单元，表达某轮对话中最终仍需展示的细节内容
- **Session Summary**: 面向列表展示的轻量会话概览，包含标题、最近一次查询预览与必要状态信息，帮助用户快速识别和选择要查看的历史会话
- **Artifact Reference**: 指向文件、报告或其他结果内容的稳定引用，用于在历史详情中再次查看最终产物

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在验收样本中，100% 的已保存会话都能仅基于原始 `sessionId` 被成功重新打开，并恢复该会话下的全部已保存轮次
- **SC-002**: 在验收样本中，100% 缺少显式最终回答块的轮次都能在历史中展示清晰结论，而不会出现“无结果”空白状态
- **SC-003**: 在验收样本中，100% 的失败或强制停止轮次在历史重开后仍能展示最后可见细节和明确终态
- **SC-004**: 在验收样本中，对比进行中结束界面与历史重开界面时，100% 的结构化会话保持相同的主要细节类别与展示顺序
- **SC-005**: 在验收样本中，100% 的会话摘要列表与对应详情页在轮次数、最新状态和最近活动信息上保持一致
- **SC-006**: 对最近会话的验收样本，95% 以上的会话在用户进入后 3 秒内可以看到首个有意义的历史内容

## Assumptions

- 当前页面在刷新或重进时仍能拿到稳定的 `sessionId`，并以此作为自动恢复当前会话的默认入口；除此之外，用户也可以从系统范围内的近期会话列表手动进入其他会话
- 现有工具输出与产物引用已经是稳定事实源，本次需求只复用这些事实，不重新定义其生产方式
- 首版自动恢复只面向当前会话，不承担“自动挑选最近一次相关会话”之类更宽泛的历史发现能力
- 只要求当前账本模型下写入的历史能够稳定恢复；不兼容的旧历史数据不在本次验收范围内
- 会话摘要与会话详情继续保持分层读取，避免为了展示会话列表而加载完整历史内容
