## Existing System Context *(mandatory for brownfield features)*

- **Existing Capabilities to Reuse**: 现有 ReAct / PlanSolve Agent 执行链路、`AgentToolCollectionFactory` 的工具装配入口、`ReactorConfig` 的工具配置装配、`ExecutorAgent` / `ReactImplAgent` 的工具结果推送机制、`Message`/`BaseAgent`/`LLM` 已具备的图文消息底座、现有 `FileTool` 产物落库与文件上传能力、`reactor-tool` 当前 `/v1/tool/*` 工具服务与流式响应模式

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 现有对话可完成多模态知识检索 (Priority: P1)

作为使用现有 Agent 对话能力的用户，我希望在不更换页面和操作方式的前提下，针对需要查询图文混合知识库的问题，直接得到多模态知识检索结果，并在当前会话中看到持续输出的回答。

**Why this priority**: 这是本次迁移的核心用户价值，也是参考项目与当前项目之间最关键的能力差异。

**Independent Test**: 在现有对话入口中发起一条文本问题，该问题需要从图文混合知识库中检索答案，验证系统能够在当前会话中完成多模态检索、持续输出结果，并生成可复用的 Markdown 产物。

**Acceptance Scenarios**:

1. **Given** 用户在现有会话中提交了一个文本问题，该问题需要从图文混合知识库中检索答案，**When** Agent 判断该任务需要多模态知识检索，**Then** 系统必须在当前对话链路内调用多模态检索能力并持续返回可阅读结果，而不要求用户切换到新的页面或使用新的入口
2. **Given** 多模态检索结果中包含图片引用或图文混合内容，**When** 检索完成，**Then** 用户必须在当前会话中看到可阅读的结果内容，并能获得与本次检索关联的 Markdown 结果产物
3. **Given** 用户的问题不需要多模态知识检索，**When** Agent 完成任务，**Then** 系统必须继续按当前既有工具链路执行，不因为本期能力迁移而改变普通任务的主流程体验

---

### User Story 2 - 运维可通过现有配置启用和管理多模态工具 (Priority: P2)

作为维护 Agent 平台的运维或配置管理员，我希望继续通过现有配置体系控制工具可用性、说明和外部地址，使多模态知识检索可以像其他工具一样被装配、启停和调整。

**Why this priority**: 如果多模态能力只能通过硬编码接入，将破坏当前项目的可维护性，也无法稳定支撑后续扩展。

**Independent Test**: 在不改前端的前提下，通过配置启用默认多模态工具、调整工具说明和外部服务地址，然后验证新配置能在 `REACT` 与 `PlanSolve` 会话中生效。

**Acceptance Scenarios**:

1. **Given** 平台启用了多模态知识检索能力，**When** 系统为 `REACT` 或 `PlanSolve` 会话装配默认工具集合，**Then** 多模态知识检索工具必须按既有规则进入默认工具集
2. **Given** 平台关闭了多模态知识检索能力或将其从默认工具列表中移除，**When** 新会话创建并装配工具，**Then** 系统不得再向该会话暴露多模态知识检索工具
3. **Given** 运维调整了多模态工具说明、入参定义或外部服务地址，**When** 新请求到达，**Then** 运行时必须使用新的配置值，无需前端改造

---

### User Story 3 - 上游异常不会拖垮既有 Agent 流程 (Priority: P3)

作为平台维护者，我希望即使多模态检索服务出现超时、空结果或格式异常，系统也能给出明确反馈并安全结束，而不是让整个 Agent 执行链路卡死、丢失结果或静默切换成其他能力。

**Why this priority**: 新接入的是外部多模态能力，如果异常隔离做不好，会直接影响当前平台稳定性。

**Independent Test**: 模拟多模态检索为空、超时、流式片段异常和服务不可达等场景，验证会话能得到明确失败反馈、不会自动退回普通搜索，且工具执行能正常结束，其他非目标流程无明显回归。

**Acceptance Scenarios**:

1. **Given** 多模态检索请求缺少有效问题或上游服务不可用，**When** Agent 触发检索，**Then** 系统必须返回明确的失败结果，并让本轮工具执行安全收口
2. **Given** 多模态检索的流式返回中出现心跳、空片段或混合格式响应，**When** 系统消费该结果，**Then** 必须尽可能恢复可用内容，无法恢复时也不得导致会话挂起或无限等待
3. **Given** 多模态检索执行失败，**When** 当前任务仍处于本轮 MRAG 工具执行上下文，**Then** 系统不得静默自动降级到普通搜索能力，而必须按失败结果结束本轮工具执行
4. **Given** 平台继续处理纯文本任务、普通搜索任务或历史会话回放，**When** 本期能力已经上线，**Then** 这些非目标路径必须保持现有可见行为和稳定性

### Edge Cases

- 用户问题为空，或文本问题不足以形成有效检索语义
- 上游多模态服务仅返回心跳、空片段、半截内容，或同时混用“增量片段”和“最终结果”两种返回风格
- 检索结果中包含图片 Markdown 引用，需要在现有展示链路中保持可读性而不是被丢弃
- 多模态工具被关闭、默认工具列表未启用该能力，或当前请求不属于 `REACT` / `PlanSolve` 可暴露该工具的链路
- 多模态检索失败后，Agent 不得因工具线程未释放而卡住整个执行流程
- 多模态检索失败后，不得静默回退为普通搜索结果并冒充成功完成
- 纯文本会话、历史回放、普通搜索/报告/文件工具链路在本期上线后必须保持兼容

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 允许现有 Agent 对话在不新增前端入口和页面改造的前提下，处理通过文本问题查询图文混合知识库的请求
- **FR-002**: 系统 MUST 向标准 Agent 工具体系提供一项独立的多模态知识检索能力，使 Agent 能在现有推理与执行流程中主动选择该能力完成任务
- **FR-003**: 系统 MUST 让多模态知识检索能力在默认 `REACT` 与 `PlanSolve` 的非 `dataAgent` 工具集合中按配置可启用、可禁用，并保持 `dataAgent` 现有工具语义不变
- **FR-004**: 系统 MUST 将多模态知识检索结果通过当前会话流式输出链路持续反馈给用户，并让该类工具结果遵循当前用户可见工具结果的展示规则
- **FR-005**: 系统 MUST 保留多模态检索返回中的图文混合内容，使图片引用和文本说明都能以现有客户端可阅读的 Markdown 形式呈现
- **FR-006**: 系统 MUST 在多模态检索成功结束后生成与当前请求绑定的 Markdown 结果产物，供后续查看、下载和继续复用
- **FR-007**: 系统 MUST 允许配置管理员通过现有配置机制管理多模态工具的可用性、说明文案、入参定义和外部服务地址，而不是依赖代码改动
- **FR-008**: 系统 MUST 为多模态知识检索提供与现有工具服务一致的请求与流式响应模式，使当前后端能够稳定消费增量结果和最终结果
- **FR-009**: 系统 MUST 在空输入、超时、上游失败、流式格式异常等场景下给出确定性的失败结果，并保证整个 Agent 执行链路能够安全结束，不发生挂起
- **FR-010**: 系统 MUST 保持纯文本任务、现有工具执行持久化、历史回放和普通会话链路的向后兼容；当本期能力未被调用时，用户不应感知到行为变化
- **FR-011**: 系统 MUST 将本期改动边界限定在当前后端 Agent 运行时、配置装配与外部工具服务扩展点内，保证前端、数据库结构和非目标能力不成为上线前置依赖
- **FR-012**: 系统 MUST 默认让 `REACT` 与 `PlanSolve` 两条 Agent 执行链路都具备多模态知识检索能力，并在结果展示、异常收口和产物生成上保持一致性
- **FR-013**: 系统 MUST 在多模态知识检索失败时返回明确失败结果，默认不得自动降级为普通搜索或其他替代工具结果
- **FR-014**: 系统 MUST 将 MRAG 相关 Python 能力并入当前 `reactor-tool` 体系进行交付与运维，不引入一套并行独立维护的长期服务形态

### Key Entities *(include if feature involves data)*

- **Multimodal Retrieval Request**: 一次与当前会话绑定的知识检索请求，包含检索问题、原始用户任务语义和流式开关，本期不要求新增用户直传图片输入
- **Multimodal Retrieval Stream Chunk**: 多模态检索过程中的增量结果单元，可能承载文本片段、最终完成标记或可恢复的图文混合内容
- **Knowledge Retrieval Artifact**: 多模态检索完成后沉淀出的 Markdown 结果产物，可被当前会话展示、下载与后续任务复用
- **Tool Availability Profile**: 当前会话可见的默认工具集合配置，决定多模态知识检索是否对该类请求开放
- **Image Context**: 与当前问题关联的图片语义输入，可来自现有请求上下文中的图片内容或可解析的图片引用

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在标准验收样本中，95% 以上需要图文混合知识理解的请求都能在现有会话内成功触发多模态检索，并在 5 秒内向用户返回首个可见结果片段
- **SC-002**: 95% 以上成功完成的多模态检索请求都会生成与当前会话绑定的 Markdown 结果产物，且用户可在当前会话链路中看到最终结果
- **SC-003**: 在包含上游超时、空输入、混合流式片段和服务不可达的异常验收场景中，100% 的请求都能得到明确结束结果，不出现会话长期挂起，也不发生静默自动降级
- **SC-004**: 在上线后的回归验收中，纯文本任务、普通搜索/报告/文件工具链路和历史会话回放的关键样本保持与基线一致，不出现高严重度可见回归
- **SC-005**: 运维能够在一次常规配置发布周期内完成多模态工具的启停或外部地址调整，而无需配合前端发布
- **SC-006**: `REACT` 与 `PlanSolve` 两类验收样本都能成功触发并完成多模态知识检索，不出现仅单链路生效的偏差

## Assumptions

- 当前前端无需新增“上传图片参与 MRAG 检索”的交互元素；本期多模态能力的范围限定为文本问题检索图文混合知识库
- 当前 `Message` / `BaseAgent` / `LLM` 的图文消息底座可继续复用，本期重点在多模态检索工具与外部服务闭环，而非重做基础消息模型
- 当前文件上传与产物展示链路足以承载多模态检索生成的 Markdown 结果文件，无需新增独立产物存储方案
- 参考项目中的 `genie-tool` MRAG 能力将作为行为基线，但当前项目优先扩展现有 `reactor-tool` 服务，而不是并行引入一套长期重复维护的独立工具体系
- 本期以“效果对齐参考项目”为目标，但允许按当前项目既有架构做等价适配，只要用户可见能力和验收结果一致
