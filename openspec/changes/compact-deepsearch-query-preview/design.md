## Context

当前 `deep_search` 已经具备完整的三阶段事件与数据：

- `extend` 阶段提供 `searchResult.query`，可直接拿到查询分解后的子问题。
- `search` 阶段提供与子问题对应的 `docs`。
- `report` 阶段提供最终总结。

问题不在协议，而在前端的信息分层。之前的方案把“搜索完成”的大卡片直接放进左侧对话区，导致：

1. 左侧消息流被大面积来源卡片占满，阅读密度变差。
2. 右侧工作区失去“详情查看面”的职责，概览和详情混在一起。
3. 用户真正关心的“正在搜哪些子问题”没有以合适的紧凑形式出现在对话上下文里。

这次设计需要把左侧对话区收敛为“概览入口”，把右侧工作区保留为“来源详情面”，同时保持实时流式与历史回放的一致性。

## Goals / Non-Goals

**Goals:**

- 在 `deep_search.extend` 阶段于对话区展示紧凑型查询分解预览，而不是右侧工作区详情。
- 每个子查询在对话区独立渲染为一个上下堆叠的搜索预览组件，明确表达“正在搜索”。
- `deep_search.search` 阶段保持左侧为紧凑且可点击的入口，点击后在右侧工作区查看对应来源列表。
- 保持 `report` 阶段继续输出总结，不把来源详情塞回对话区。
- 让实时流式和历史回放复用同一套 deep_search 视图映射逻辑。

**Non-Goals:**

- 不修改 deep_search 后端协议、字段结构或搜索执行逻辑。
- 不把真实来源卡片重新搬回左侧对话区。
- 不重做整个工作区体系，只调整 deep_search 在左侧与右侧的职责边界。
- 不引入新的持久化结构或数据库变更。

## Decisions

### Decision 1: 左侧对话区只承担 deep_search 的“概览入口”

采用方案：

- `extend` 阶段在左侧展示查询分解预览组件。
- `search` 阶段在左侧保留紧凑的“搜索完成”入口组件。
- 真实来源条目只在右侧工作区展示。

原因：

- 用户要的是“知道系统正在搜什么”，不是在消息流里直接读完所有来源详情。
- 左概览、右详情的分层更符合当前页面布局，也减少对话区纵向占用。

备选方案：

- 方案 A：继续把来源卡片直接渲染到对话区。问题是占位过重，与用户反馈相反。

### Decision 2: 继续按子查询拆分 deep_search 子项，而不是在对话区聚合成单卡片

采用方案：

- 保持 `handleTaskData/processDeepSearchTask` 现有的按 query 拆分能力。
- 对话区对每个子查询渲染一个紧凑预览项；如果拆分出两条查询，就显示上下两个组件。

原因：

- 这与用户明确提出的“分成上下两个组件展示”完全一致。
- 每个子查询对应一个可点击入口，也便于右侧工作区展示对应的来源详情。

备选方案：

- 方案 A：把多个子查询聚合成一个列表卡片。问题是和用户要的“一条一个组件”不一致，也弱化了逐项点击查看详情的能力。

### Decision 3: 为 deep_search 增加“紧凑预览”视图模型，而不是复用完整结果卡片布局

采用方案：

- 抽离共享的 deep_search 数据映射层，分别产出：
  - 对话区紧凑预览模型：展示子查询标题、状态、加载态。
  - 工作区详情模型：展示真实来源列表。
- 视觉语言沿用搜索组件，但尺寸、信息密度、交互语义针对对话区做紧凑化。

原因：

- 左侧和右侧展示的是不同层级的信息，直接复用完整结果卡片会导致布局过重。
- 共享数据映射可以避免实时流与回放各写一套逻辑。

备选方案：

- 方案 A：完全复制一套对话区组件。问题是状态映射和样式维护容易分叉。
- 方案 B：直接让 `SearchListRenderer` 同时承担左侧紧凑态与右侧详情态。问题是组件语义过于混杂。

### Decision 4: `search` 阶段通过左侧点击激活右侧工作区，而不是在阶段切换时自动展开

采用方案：

- `search` 阶段左侧预览项继续作为可点击 task 入口。
- 用户点击对应入口后，右侧工作区显示该子查询的来源条目。

原因：

- 自动展开会打断阅读流，也会让右侧面板频繁抢焦点。
- 当前项目已有 `changeTask -> ActionPanel` 链路，可直接复用。

备选方案：

- 方案 A：搜索完成后自动切到右侧。问题是交互过于激进，且不符合“用户点击后再看详情”的预期。

### Decision 5: `report` 阶段继续独立于查询预览/来源详情

采用方案：

- `extend` 与 `search` 只负责查询概览入口和详情入口。
- `report` 继续走总结内容渲染链路。

原因：

- 这样可以让 deep_search 的阶段职责清晰，不把“过程概览”和“最终结论”混成一块。

## Risks / Trade-offs

- [左侧紧凑预览做得过轻，用户不容易意识到可点击] → 保留明确的状态文案、搜索图标和 hover/click 反馈。
- [按子查询拆分后，右侧详情被分散成多个入口] → 保持一条子查询对应一组来源，避免点击后看到混杂结果。
- [实时流和回放状态不一致] → 统一从消息归一化层产出 deep_search 预览模型与详情模型。
- [已有错误实现与本次方向冲突] → 以本变更为准，恢复“左侧概览、右侧详情”的职责边界。

## Migration Plan

1. 梳理当前 deep_search 在 `Dialogue`、`ActionPanel`、消息归一化中的左右区域职责。
2. 抽离 deep_search 的紧凑预览模型与工作区详情模型。
3. 调整 `Dialogue` 仅渲染 `extend/search` 的紧凑预览入口，并按子查询逐条展示。
4. 保持 `ActionPanel` 仅在选中 deep_search 子项时显示真实来源列表。
5. 补充历史回放与点击联动验证后上线。

回滚策略：

- 回退到当前稳定的 deep_search 工作区展示链路；
- 移除对话区紧凑预览组件接入，恢复原有任务摘要入口。

## Open Questions

- `search` 阶段左侧完成态是否需要显示“搜索完成”字样，还是仅保留子查询标题和完成图标；本次默认保留明确状态文案。
- 如果某个子查询没有搜到来源，右侧工作区是否显示空态；本次默认显示空态而不是隐藏入口。
