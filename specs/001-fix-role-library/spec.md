## Clarifications

### Session 2026-04-11

- Q: 角色库成员范围如何确定？→ A: 不新增角色标记，所有启用且满足 Fix 条件的智能体自动进入角色库
- Q: 会话内是否允许切换角色？→ A: 不允许，换角色必须新建会话
- Q: chat 模式默认入口如何与角色库共存？→ A: chat 模式右侧提供角色库按钮；未主动选择时默认使用第一个角色，即现有 chat 角色
- Q: 默认角色如何稳定确定？→ A: 默认角色固定为现有 chat 角色，且在角色库中始终排第一

## Existing System Context *(mandatory for brownfield features)*

- **Affected Modules**: 智能体配置域、固定对话执行链路、会话持久化链路、前端聊天入口与会话展示
- **Existing Capabilities to Reuse**: 现有智能体主记录及其关联配置、现有固定执行模式、现有可用智能体查询能力、现有会话与消息持久化能力、现有前端会话列表与聊天界面
- **Out of Scope**: 深度思考与 React 模式重构、独立的新角色引擎、与 Fix 模式无关的智能体链路改造、复杂的角色运营后台重做
- **Current Constraints**: 角色库必须建立在现有智能体记录之上，避免维护平行的角色数据源；用户选中的角色必须真正影响聊天行为，而不是只改前端展示；方案应保持结构简洁、职责清晰、便于后续继续扩展角色

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 选择角色开始对话 (Priority: P1)

普通用户进入 chat 模式后，可以通过聊天区域右侧的角色库按钮查看并选择角色开始聊天。如果用户没有主动选择角色，系统会默认使用当前首个角色，也就是现有 chat 角色。选中的角色会直接决定这次对话使用的固定模式能力、话术和工具组合，让用户明显感知到不同角色的回答风格和能力边界。

**Why this priority**: 这是角色库存在的核心价值。没有“可选择角色并按角色真实对话”，角色库就只是静态展示，无法增强平台的角色多元性。

**Independent Test**: 用户在前端选择任意一个可用角色，发起首轮对话后，系统能返回该角色对应的对话结果；切换为另一个角色重新发起新对话后，返回结果体现出不同的角色配置。

**Acceptance Scenarios**:

1. **Given** 平台中存在多个可用于固定模式对话的角色，**When** 用户打开聊天页面，**Then** 系统展示角色列表并允许用户选择其中一个角色
2. **Given** 用户已选择某个角色，**When** 用户发送第一条消息，**Then** 系统按该角色对应的固定模式配置执行对话并返回结果
3. **Given** 用户未主动打开角色库选择角色，**When** 用户在 chat 模式直接发送第一条消息，**Then** 系统默认使用首个角色开始固定模式对话
4. **Given** 用户新建另一段对话并选择不同角色，**When** 用户发送消息，**Then** 新对话使用新角色，且不会污染之前会话的角色上下文
5. **Given** 用户打开角色库面板，**When** 系统展示角色列表，**Then** 现有 chat 角色始终排在第一位并作为默认角色

---

### User Story 2 - 基于现有智能体记录维护角色库 (Priority: P2)

平台维护人员希望继续基于现有智能体记录和关联配置维护角色，而不是再创建一套重复的角色数据。只要某个角色满足固定模式对话所需条件，就可以被纳入角色库并对前端可见。

**Why this priority**: 这是保证方案优雅和可维护的关键。如果角色库另起炉灶，就会和现有智能体配置产生双份维护，长期成本高且容易失真。

**Independent Test**: 维护人员基于现有智能体记录补齐或调整角色配置后，无需新增平行角色定义即可让角色进入或退出角色库展示范围。

**Acceptance Scenarios**:

1. **Given** 某个现有智能体记录已经具备固定模式对话所需配置且处于启用状态，**When** 用户刷新角色列表，**Then** 该角色会自动出现在前端角色库中
2. **Given** 某个角色已被停用或不再满足展示条件，**When** 用户刷新角色列表，**Then** 该角色不再作为可选角色展示

---

### User Story 3 - 会话中持续保留所选角色 (Priority: P3)

用户在一段已经开始的会话中，希望系统持续使用最初选择的角色，而不是因为刷新页面、重新进入会话或查看历史记录而丢失角色语义。同一会话内不允许直接切换到另一个角色，避免不同角色的上下文相互污染。角色绑定以会话为单位持久化，保证历史回放和继续对话时都能恢复到同一个角色。

**Why this priority**: 如果会话无法稳定记住角色，用户会感到角色只是“入口皮肤”，不是实际参与对话的智能体，体验会明显割裂。

**Independent Test**: 用户进入已存在的角色会话，继续追问同一主题时，系统仍然沿用该会话绑定的角色，且历史列表中可以识别该会话属于哪个角色。

**Acceptance Scenarios**:

1. **Given** 用户已经创建了一段绑定角色的会话，**When** 用户刷新页面后重新进入该会话，**Then** 系统仍然识别并展示该会话所属角色
2. **Given** 用户在该会话中继续发送消息，**When** 系统处理请求，**Then** 仍沿用原角色，不要求用户重复选择
3. **Given** 某个会话绑定的角色后来下线，**When** 用户打开历史会话，**Then** 系统能提示该角色当前不可继续使用，并提供合理的后续选择

### Edge Cases

- 当平台里没有任何可用于固定模式对话的角色时，系统如何提示用户并避免出现空白页面？
- 当用户通过旧链接或历史记录打开一个已经不可用的角色会话时，系统如何保证历史可读且后续操作可预期？
- 当某个角色有智能体主记录但缺少必要关联配置时，系统如何避免把一个“不可真正对话”的角色暴露给用户？
- 当用户在已有会话中试图切换角色时，系统应阻止在原会话内直接切换，并引导用户新建会话后再选择新角色

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 基于现有智能体记录提供一个可供前端展示的 AI 角色库，并展示每个角色的基础识别信息
- **FR-002**: 用户 MUST be able to 在 chat 模式中通过角色库按钮选择一个角色，并以该角色开始固定模式对话
- **FR-003**: 系统 MUST 保证角色选择真正影响对话执行结果，而不是只影响前端文案或展示样式
- **FR-004**: 系统 MUST 在同一会话内持续绑定并沿用用户最初选择的角色；若用户想使用其他角色，必须通过新建会话重新选择
- **FR-005**: 系统 MUST 仅向前端暴露当前可正常参与固定模式对话的角色，不向用户展示无法执行的伪角色
- **FR-006**: 系统 MUST 以现有智能体记录作为角色库的唯一事实来源，避免维护重复的独立角色主数据
- **FR-007**: 系统 MUST 依据现有智能体启用状态和固定模式可执行条件自动推导角色库成员范围，并基于现有智能体相关配置决定角色进入后使用哪套固定模式能力
- **FR-008**: 系统 MUST 在会话级别持久化角色绑定关系，并在会话列表、会话详情或继续对话场景中返回该角色标识，让用户知道自己正在与哪个角色对话
- **FR-009**: 系统 MUST 在用户选择的角色失效、停用或配置不完整时，给出清晰可理解的反馈，并阻止错误对话继续发起
- **FR-010**: 系统 MUST 保持现有非角色化对话能力可平滑演进，不因为引入角色库而破坏既有聊天主链路
- **FR-011**: 系统 MUST 在用户未主动选择角色时，默认使用角色库中的首个角色作为 chat 模式的固定模式入口
- **FR-012**: 系统 MUST 让 chat 模式入口与角色库共存，用户既可以直接使用默认角色开始聊天，也可以先打开角色库切换到其他角色
- **FR-013**: 系统 MUST 将现有 chat 角色固定为默认角色，并保证它在角色库列表中的优先位置稳定不变

### Key Entities *(include if feature involves data)*

- **AI 角色**: 平台中可被用户选择并用于固定模式对话的智能体实体，包含角色名称、简介、是否可选、对话入口形态等基础信息
- **角色可用规则**: 用于判断某个现有智能体是否能自动进入角色库的一组既有条件，至少要求该智能体已启用且能够完成固定模式对话
- **角色会话**: 一段绑定了特定角色的用户对话，会在会话层面持久记录该角色身份，确保后续追问、历史回放和刷新恢复都沿用同一角色
- **角色能力配置**: 某个角色进入角色库并参与固定模式对话所依赖的现有配置集合，用于定义该角色的能力边界和对话行为

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户进入聊天页面后，可以在 10 秒内识别并完成一个角色的选择，然后成功开始首轮对话
- **SC-002**: 100% 的角色化会话在刷新页面、重新进入历史记录后，仍能正确识别并展示原始角色
- **SC-003**: 100% 的前端可见角色都能够成功发起固定模式对话，不出现“能选但不能聊”的情况
- **SC-004**: 平台维护人员在补齐现有智能体配置后，无需引入额外重复角色主数据，就能让一个新角色进入角色库
- **SC-005**: 当用户选择失效角色或继续访问失效角色会话时，系统能在一次交互内给出清晰反馈并指向可执行的下一步操作

## Assumptions

- 首期角色库仅覆盖固定模式对话场景，不要求同时支持深度思考与 React 模式
- 首期角色展示信息默认复用现有智能体名称与描述等基础信息，不强制要求引入复杂的角色装饰信息
- 角色的能力差异主要来自现有智能体及其关联配置，而不是临时拼装的前端提示词
- 角色库首期不额外增加显式“是否入库”人工标记，而是自动暴露所有启用且满足固定模式对话条件的智能体
- 同一段会话默认只绑定一个角色；如果用户想体验另一个角色，将通过新建会话重新选择的方式开始
- 默认角色不通过新增独立排序配置维护，而是直接固定为现有 chat 角色并保持其在角色库中的首位
- 角色绑定关系以会话为唯一持久化单位，不在每条消息层面重复维护角色归属
- 现有智能体配置维护方式仍然可继续使用，首期不强制新增专门的角色后台管理界面
