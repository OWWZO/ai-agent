## Existing System Context *(mandatory for brownfield features)*

- **Affected Modules**: `ai-agent-station-study-domain`、`ai-agent-station-study-trigger`、`ai-agent-station-study-app`、`ui`
- **Existing Capabilities to Reuse**: 现有 `sessionId` 会话归属与模式守卫、现有请求生命周期与流式执行入口、现有稳定文件/产物引用能力、现有会话列表与历史详情入口、现有会话级持久化与查询装配边界
- **Out of Scope**: 不保留旧历史结构兼容读取、不为旧表做迁移桥接、不新增跨会话长期用户画像、不改 `reactor-tool/` 与 `reactor-client/`、不把普通 `CHAT` 模式纳入本期彻底重写
- **Current Constraints**: MySQL 仍是会话历史、上下文恢复和压缩快照的真相源；续聊、历史重开和压缩必须共用同一套持久化事实；必须遵守 DDD 分层；上线切换后允许直接删除旧链路与旧数据；新方案不得再依赖多级 normalizer、assembler 或回放兼容层

## Clarifications

### Session 2026-04-28

- Q: 会话压缩触发时机是什么？ → A: 每次新请求开始前同步判断；超阈值时先压缩，再执行当前请求
- Q: 历史展示读模型如何生成？ → A: 同步双写独立展示读模型；与会话事实在同一事务内落库
- Q: 压缩失败时当前请求如何处理？ → A: 压缩失败后直接跳过压缩，始终继续当前请求
- Q: 会话记忆快照如何保留？ → A: 同一会话保留多版本记忆快照；运行时只读取最新有效版本
- Q: 上线切换时如何处理旧代码和旧表结构？ → A: 上线切换时直接删除旧表对应代码与旧表结构，只保留新事实模型

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 同会话续聊沿用单一事实链 (Priority: P1)

作为在同一会话里连续推进任务的用户，我希望系统下一轮请求能直接知道前面已经做过什么、得到过什么结果、产出过什么文件，并继续当前任务，而不是因为旧链路切换和多层转换导致“记忆断掉”或重复劳动。

**Why this priority**: 这是本次重写的核心价值。只要续聊仍然依赖旧账本兼容、前端回放拼装或多次中间转换，复杂任务就会继续出现失忆、重复搜索和重复调用工具的问题。

**Independent Test**: 在同一 `sessionId` 内先完成一轮包含工具调用、结果观察和文件产出的复杂任务，再发起“继续刚才任务”或“基于上次结果补充”的下一轮请求，验证系统能直接继承上一轮的任务状态、关键事实和产物引用。

**Acceptance Scenarios**:

1. **Given** 某会话上一轮已经完成搜索、工具调用和文件产出，**When** 用户在同一会话里要求“继续刚才的任务”，**Then** 系统必须直接基于持久化事实继续工作，而不是要求用户重新描述此前发生过的步骤
2. **Given** 某会话上一轮已经得到多个工具结果且其中一部分会影响下一步决策，**When** 用户在下一轮引用这些结果继续推进任务，**Then** 系统必须能区分这些结果的顺序、来源和关联关系
3. **Given** 某会话上一轮已经生成稳定文件或产物引用，**When** 用户要求“基于刚才生成的内容继续修改”，**Then** 系统必须恢复这些引用并继续使用，而不是仅保留一段最终回答摘要

---

### User Story 2 - 历史重开与实时续聊共享同一记忆来源 (Priority: P2)

作为重新打开旧会话继续工作的用户，我希望历史重开后的第一轮请求和实时续聊使用同一套会话事实与记忆来源，这样我看到的历史和系统真正能记住的历史不会再分裂成两套模型。

**Why this priority**: 当前痛点不只是“能否展示历史”，而是“展示得到的历史”和“模型可用的历史”并不一致。重写后两条链路必须统一，否则用户仍然会遇到“看得到但用不到”的断层。

**Independent Test**: 完成一条包含多步执行、工具结果和文件产物的会话，关闭后重新打开该会话继续提问，验证系统恢复出的任务状态、关键事实和产物引用与同一会话在线续聊时一致。

**Acceptance Scenarios**:

1. **Given** 某会话已完成多轮任务推进并持久化了完整执行事实，**When** 用户重新打开该会话并继续提问，**Then** 系统必须恢复与在线续聊一致的任务状态和关键上下文
2. **Given** 某会话历史中存在思考过程、工具调用、工具结果和文件引用，**When** 用户在重开后继续工作，**Then** 系统必须继续感知这些事实，而不是只读取最后一条答复
3. **Given** 某会话历史详情中展示了关键过程块与文件入口，**When** 用户基于这些内容继续追问，**Then** 系统使用的可续聊上下文必须与这些持久化事实保持一致

---

### User Story 3 - 长会话压缩后继续任务不丢状态 (Priority: P3)

作为执行长链路任务的用户，我希望会话被压缩后，系统仍然保留当前任务状态、关键结论、关键约束、待办事项和最近真实执行链，这样我不用担心压缩把任务变成一段无用摘要。

**Why this priority**: 如果压缩后只剩模糊总结，用户虽然“有记忆”，但无法继续真正的工作链。压缩必须服务于持续执行，而不是只为了节省上下文长度。

**Independent Test**: 构造一条超过压缩阈值的复杂会话，在压缩发生后立刻追问当前任务、上一步结果或下一步安排，验证系统仍能恢复当前状态、关键事实和最近执行链。

**Acceptance Scenarios**:

1. **Given** 某会话已有一部分历史被压缩为会话记忆，且后续又产生了新的已完成轮次，**When** 用户继续当前任务，**Then** 系统必须把压缩记忆和边界之后的事实组合成可工作的上下文
2. **Given** 某会话最近轮次中包含重复工具调用、长结果和文件产出，**When** 压缩后用户追问最近一次操作，**Then** 系统必须保留最近执行链的顺序和关键结果，而不是混淆不同调用
3. **Given** 某会话中存在超长报告或超长命令输出，**When** 系统执行压缩并继续续聊，**Then** 系统必须保留关键结果和稳定引用，同时避免把整段超长内容再次内联成工作记忆

### Edge Cases

- 未完成、报错或被强制停止的轮次不能进入可复用上下文，也不能进入压缩输入
- 同一工具在同一轮或相邻轮中多次调用时，系统必须保留每次调用的先后顺序和结果对应关系
- 当会话已经存在压缩边界但边界之后没有新的已完成事实时，系统不能重复生成无意义的新记忆版本
- 压缩失败时，系统必须放弃本次压缩结果并继续当前请求，不能写入半成品记忆或半成品边界
- 当稳定文件或产物引用已经失效时，系统必须显式标记该引用不可复用，而不是静默丢失这段历史
- 只有最终回答、没有额外工具调用的轻量轮次也必须能被续聊和压缩正确处理
- 上线切换后的旧结构数据允许直接清理；系统不需要为旧结构历史提供继续可读或可续聊能力
- 同一 `sessionId` 发生模式冲突或上一轮尚未结束时，系统必须拒绝新请求，不能让新方案绕过既有守卫

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 以单一的会话事实链作为新会话的唯一真相源，用于续聊、历史重开和压缩；同一会话不得再存在“展示历史一套模型、工作记忆另一套模型”的分裂
- **FR-002**: 系统 MUST 把每个已完成轮次表达为有序的轮次元数据与有序的语义块集合，使用户输入、助手思考、工具调用、工具结果、产物引用和最终回答都能被直接读取和恢复
- **FR-003**: 系统 MUST 仅支持固定且有限的语义块类型集合，至少覆盖用户输入、助手思考、工具调用、工具结果、产物引用和最终回答；不再接受无边界扩散的临时块类型
- **FR-004**: 系统 MUST 让同一轮内的语义块顺序、工具调用与结果关联、重复调用关系以及产物生成顺序保持稳定，可被后续轮次直接感知
- **FR-005**: 系统 MUST 让续聊上下文直接来源于会话事实链，而不是依赖旧消息恢复器、回放拼装器或多层中间格式转换后再二次组装
- **FR-006**: 系统 MUST 让历史重开后的第一轮请求与实时续聊复用同一套事实恢复语义，确保用户在两种入口下获得一致的任务状态、关键事实和产物引用
- **FR-007**: 系统 MUST 保留稳定文件和产物引用的可续聊能力；对体量过大的原始内容，应优先保留关键结果与稳定引用，而不是重复存储或重复回灌全文
- **FR-008**: 系统 MUST 维护明确的会话记忆边界，只把边界之前的已完成历史沉淀为会话记忆快照，并把边界之后的事实直接作为当前工作上下文的一部分
- **FR-008A**: 系统 MUST 在每次新请求真正进入主执行前同步判断是否需要压缩；一旦达到阈值，必须先完成压缩并生成可用的最新会话记忆，再执行当前请求
- **FR-009**: 系统 MUST 在需要压缩时生成新的会话记忆版本，该记忆必须能表达当前任务状态、关键结论、关键约束、待办事项、关键文件/产物和可复用事实
- **FR-009B**: 系统 MUST 为同一会话保留多版本会话记忆快照；运行时默认只读取最新有效版本，历史版本保留用于回溯、排障和重建边界
- **FR-009A**: 若压缩执行失败，系统 MUST 放弃本次压缩结果并直接继续当前请求；失败的压缩尝试不得产出半成品会话记忆、半成品边界或污染后续上下文
- **FR-010**: 系统 MUST 只允许已完成轮次进入会话记忆和续聊上下文；`STREAMING`、`ERROR`、`FORCE_STOPPED` 等未完成状态不得污染后续可复用事实
- **FR-011**: 系统 MUST 保留面向前端的独立历史展示读模型，但该读模型必须与工作记忆来源于同一次持久化事实，避免再通过前端临时状态反推历史
- **FR-011A**: 系统 MUST 在写入会话事实时同步双写历史展示读模型，并与会话事实在同一事务内完成持久化，保证历史查询不再依赖运行时拼装或异步补投影
- **FR-012**: 系统 MUST NOT 在新方案中保留旧持久化结构的兼容读取、兼容写入、兼容投影或兼容压缩逻辑；上线切换后的主链路只服务新的事实模型
- **FR-013**: 系统 MUST 允许上线时清理或忽略旧结构历史数据，不要求旧历史在切换后继续可读、可续聊或可压缩
- **FR-013A**: 系统 MUST 在上线切换时直接删除旧表对应代码与旧表结构，只保留新的会话事实模型、会话记忆模型和展示读模型，避免主链路继续背负遗留存储
- **FR-014**: 系统 MUST 继续遵守单会话模式唯一性和并发守卫：同一 `sessionId` 不能混用不兼容执行模式，也不能在上一轮未结束时接收新的续聊请求
- **FR-015**: 系统 MUST 让续聊、历史重开和压缩完全依赖持久化事实恢复，而不是依赖进程内残留状态、前端缓存状态或人工补写的临时字段
- **FR-016**: 系统 MUST 明确领域职责边界：`domain` 持有会话事实、记忆边界、压缩语义和读模型投影规则，`trigger` 只暴露查询与调用契约，`app` 负责持久化结构和映射装配，`ui` 仅消费读模型
- **FR-017**: 系统 MUST 定义新会话事实链、会话记忆快照、压缩边界和展示读模型的最小契约变更，并同步删除不再属于新链路的旧契约
- **FR-018**: 系统 MUST 让重写后的主链路保持“单一事实模型直达读写”的设计原则，禁止同一份数据在持久化、上下文构建、压缩和历史查询之间经过多轮语义改写

### Key Entities *(include if feature involves data)*

- **Turn Ledger**: 会话中的一轮完整请求记录，承载轮次顺序、请求身份、状态和该轮用户问题
- **Transcript Block**: 从属于某轮请求的最小语义事实单元，用来表达用户输入、助手思考、工具调用、工具结果、产物引用或最终回答
- **Session Memory Snapshot**: 覆盖某个历史边界之前已完成事实的会话记忆版本，用来概括当前任务状态、关键结论、约束、待办和可复用产物
- **Session Memory Snapshot Version**: 同一会话在不同压缩时刻生成的一版有效或历史记忆快照；运行时只消费最新有效版本
- **Compaction Boundary**: 区分“已沉淀进会话记忆的历史”和“仍需直接参与工作上下文的最新事实”的分界点
- **Display History Read Model**: 面向前端历史详情的稳定读取结果，完整表达用户需要看到的过程细节，但来源仍然是同一份持久化事实
- **Working Context Window**: 一次新请求真正使用的上下文窗口，由最新有效会话记忆和边界之后的直接事实共同组成

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在验收样本中，100% 的同会话续聊请求都能继承上一轮的任务状态、关键工具结果和稳定产物引用，而不需要用户重新描述这些历史事实
- **SC-002**: 在历史重开验收样本中，100% 的第一轮续聊都能恢复与在线续聊一致的关键事实、当前任务状态和产物引用
- **SC-003**: 在包含复杂工具链的长会话样本中，由于上下文丢失导致的重复工具执行比例，相比当前旧链路降低至少 80%
- **SC-004**: 在触发压缩的验收样本中，100% 的压缩后续聊都能恢复当前任务状态、关键结论、关键约束、待办事项和稳定产物引用
- **SC-005**: 在包含超长报告或超长工具输出的验收样本中，100% 的续聊都能保留关键结果和稳定引用，同时避免把整段超长内容再次作为工作记忆内联
- **SC-006**: 上线切换后的新会话样本全部仅依赖新事实模型完成续聊、历史重开和压缩，不再触发旧兼容读取或旧链路回放

## Assumptions

- 上线切换时允许清理旧结构历史数据，因此本期无需承担旧数据兼容责任
- 本期优先覆盖 `REACT` 与 `PLAN_SOLVE` 主链路；普通 `CHAT` 模式如受公共抽象影响，仅做最小必要对齐
- 现有稳定文件/产物服务仍可提供后续续聊和历史重开所需的稳定引用
- 当前会话模式守卫、会话并发守卫和请求生命周期入口可继续复用，只重写其内部持久化事实与记忆恢复机制
- 前端可以继续消费既有或最小演进后的历史读模型，但不会再依赖旧历史兼容路径
