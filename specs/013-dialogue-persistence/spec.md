## Existing System Context *(mandatory for brownfield features)*

- **Affected Modules**: `ai-agent-station-study-domain`、`ai-agent-station-study-infrastructure`、`ai-agent-station-study-app`
- **Existing Capabilities to Reuse**: 现有 `requestId`/`sessionId` 请求归属链路、现有 `LLM.ask()` / `LLM.askTool()` 生命周期、现有 `BaseAgent.executeTools()` 并发执行模型、现有 `ToolArtifactRegistry` 产物归属能力、现有稳定文件引用与会话查询维度
- **Out of Scope**: 不保存完整聊天 transcript、不保存 provider 原始响应包、不做逐 chunk 流式落库、不引入消息队列或异步审计管线、不改 `ui/`、`reactor-tool/`、`reactor-client/`、不提供面向普通用户或后台产品化入口的执行账本查询能力、首期不覆盖 Workflow 执行链路
- **Current Constraints**: 新账本必须以单次 run 为唯一执行聚合根；写入采用同步实时的前插后更模式；持久化失败不能阻断主执行结果；本期默认完整保存模型响应、工具入参与结果正文，依赖内部排障使用边界控制风险；首期不做自动清理或保留期裁剪；不得把新账本重新接回已废弃或正在退出主链路的旧消息账本

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 排查单次执行全链路 (Priority: P1)

作为排查一次复杂对话执行问题的研发或运维人员，我希望能直接按一次请求查看完整执行账本，知道本次执行调用了哪些模型、下发了哪些工具、产出了哪些文件、最终成功还是失败，而不是再手工拼接多处日志。

**Why this priority**: 这是本期最核心的交付价值。只要单次执行链路仍然不可直接查询，后续的工具分析、问题复盘和文件追溯都会继续依赖低效的人肉排查。

**Independent Test**: 构造一条包含多次模型调用、至少一次工具调用和至少一个产物的执行样本，再按本次请求唯一标识查询，验证可以一次性得到执行总览、模型调用顺序、工具调用顺序和产物列表。

**Acceptance Scenarios**:

1. **Given** 某次请求在一次执行里触发了多次模型调用和工具调用，**When** 排查人员按该请求唯一标识查看执行账本，**Then** 系统必须返回该次执行的总览状态、按决策顺序排列的模型调用、按归属关系排列的工具调用和对应产物
2. **Given** 某次请求在执行过程中失败、超时或被停止，**When** 排查人员查看该次执行账本，**Then** 系统必须保留终态、错误信息以及失败前最后一个已记录的关键步骤

---

### User Story 2 - 分析工具近期行为与稳定性 (Priority: P2)

作为工具能力负责人，我希望能直接查看某个工具最近的调用输入、输出、状态和耗时，用来判断它最近是否容易失败、是否经常收到异常参数，以及它在一次模型决策里是如何被调度的。

**Why this priority**: 执行账本不仅要能还原单次请求，还要能支撑工具层面的持续治理，否则系统仍然无法快速发现高失败率工具或异常调用模式。

**Independent Test**: 为同一工具构造多条近期调用样本，其中包含成功、失败和并发分发场景，再按工具名称查询最近调用，验证能够看到每次调用的输入、输出、状态、耗时及其在同批决策中的原始顺序。

**Acceptance Scenarios**:

1. **Given** 某个工具最近已经被多次调用，**When** 工具负责人查看该工具最近调用记录，**Then** 系统必须提供每次调用的输入、输出或结果摘要、执行状态和耗时
2. **Given** 同一次模型决策返回了多个并发工具调用，**When** 工具负责人查看这些工具记录，**Then** 系统必须同时保留模型给出的原始分发顺序，并能区分真实执行时间线

---

### User Story 3 - 追踪输入文件与工具产物归属 (Priority: P3)

作为需要复盘某次执行文件来龙去脉的支持人员，我希望知道一次执行里有哪些用户输入文件和工具输出文件，以及每个输出文件来自哪次工具调用，这样我可以快速确认文件来源、定位异常文件和回答“这个文件是谁生成的”。

**Why this priority**: 文件一旦脱离执行归属关系，就很难支撑后续复盘、追责和复用，尤其是同一次执行可能产生多个文件、多个工具调用的场景。

**Independent Test**: 构造一条既包含用户上传输入文件、又包含工具输出文件的执行样本，再按本次执行查询文件记录，验证输入文件归属于 run，输出文件归属于具体工具调用且可回溯到该次执行。

**Acceptance Scenarios**:

1. **Given** 某次执行既包含用户上传文件，也包含工具生成文件，**When** 支持人员查看该次执行的文件账本，**Then** 系统必须区分输入文件和输出文件，并标明每个输出文件的来源工具调用
2. **Given** 某次工具调用产出了多个文件或没有产出文件，**When** 支持人员查看该次执行的文件账本，**Then** 系统必须正确记录多个文件的归属关系，且不能为没有文件的调用生成伪产物记录

### Edge Cases

- 某次执行在生成最终总结前异常退出时，账本仍必须保留已开始和已完成的关键步骤
- 同一次模型决策可能返回零个、一个或多个工具调用，账本都必须能稳定表达
- 同批工具调用会并发执行，账本必须区分“模型分发顺序”和“真实执行时间线”
- 某次工具调用只有文本结果、只有结构化结果或两者都为空时，账本都必须有一致的完成状态表达
- 同一次执行可能只有输入文件没有输出文件，或只有输出文件没有额外输入文件，账本不能混淆两类来源
- 单个持久化写入失败时，主执行链路仍需继续完成其本来能够完成的对话任务，同时留下可追踪的失败信息

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 在每次对话执行开始时创建一条 run 级总账记录，并把该次请求唯一标识和所属会话关联到这条记录
- **FR-002**: 系统 MUST 以单次 run 作为该次执行唯一的聚合根，使模型调用、工具调用、文件产物和最终状态都归属于同一条执行账本
- **FR-003**: 系统 MUST 把每次模型调用记录为独立且有序的执行事实，至少覆盖调用阶段、调用类型、完整响应文本、工具调用数量、状态、耗时和配额指标
- **FR-004**: 系统 MUST 把每次工具执行记录为独立执行事实，至少覆盖其来源模型调用、同批分发顺序、输入内容、输出内容、状态和耗时
- **FR-005**: 系统 MUST 把用户输入文件与工具输出文件记录为稳定产物事实，并确保它们归属于父级 run；其中工具输出文件还必须归属于其来源工具调用
- **FR-006**: 系统 MUST 保留 `run -> model invocation -> tool invocation -> artifact` 的因果关系，使排查人员既能还原模型决策链，也能追踪单个文件或工具结果的来源
- **FR-007**: 系统 MUST 在生命周期关键节点采用“先登记开始、结束后回写结果”的写入方式，确保执行中断时仍然保留可诊断的中间事实
- **FR-008**: 系统 MUST 区分同一批工具调用的原始分发顺序与真实执行时间线，避免并发执行时丢失模型决策顺序
- **FR-009**: 系统 MUST 在 run 结束时汇总并持久化执行级指标，至少覆盖模型调用次数、工具调用次数、产物数量、总配额指标、最终状态和最终结果摘要或错误信息
- **FR-010**: 系统 MUST 让账本持久化失败与主对话执行结果解耦；只要主执行逻辑本身可继续，记录失败不得直接中断用户本次任务
- **FR-011**: 系统 MUST 仅依赖执行账本本身就能支持三类内部排障与治理查询诉求：单次执行链路查询、按工具查看近期调用、按会话查看最近执行及相关产物
- **FR-012**: 系统 MUST 复用现有运行时已经稳定存在的唯一标识和归属能力，包括单次请求唯一标识、单次工具调用唯一标识以及现有产物归属注册能力，而不是为同一事实平行引入第二套身份体系
- **FR-013**: 系统 MUST 明确职责边界：`domain` 负责定义账本语义、记录模型和领域接口，`infrastructure` 与 `app` 负责表结构、持久化映射和内部查询落地；本期不要求 `trigger` 提供正式查询入口
- **FR-014**: 系统 MUST 定义并交付执行总账、模型调用、工具调用和文件产物所需的持久化结构及最小查询契约变更，且这些变更不得重新依赖旧消息账本
- **FR-015**: 系统 MUST 保持本期范围只针对执行账本，不扩展到完整聊天正文保存、原始 provider 包归档、逐 chunk 流式落库、异步审计管线或前端/Python 子系统重写
- **FR-016**: 系统 MUST 避免在同一次执行内重复登记同一稳定文件引用，确保文件账本对同一来源文件不会产生重复归属记录
- **FR-017**: 系统 MUST 保留模型完整响应文本、工具入参与工具输出正文作为内部排障事实源；本期不要求对这些内容做默认脱敏、摘要化或删减
- **FR-018**: 系统 MUST 在首期完整覆盖 ReAct 与 PlanSolve 两条主执行链路的 run、模型调用、工具调用和产物落账；Workflow 链路不属于本期交付范围
- **FR-019**: 系统 MUST 在首期默认长期保留执行账本记录，不提供自动清理、自动归档或按固定周期裁剪的能力
- **FR-020**: 系统 MUST 为执行账本写入结果提供内部运维信号；当写入成功率下降或出现失败时，至少能够通过错误日志和失败计数/成功率指标被识别与统计

### Key Entities *(include if feature involves data)*

- **Dialogue Run**: 一次对话执行的总账对象，表达该次请求的唯一身份、所属会话、入口类型、最终状态、聚合指标与总结信息
- **LLM Invocation**: run 内一次独立模型调用事实，表达调用阶段、顺序、完整文本响应、工具调用数量、状态、耗时和配额指标
- **Tool Invocation**: 某次模型决策下发的一次工具执行事实，表达来源模型调用、原始分发顺序、输入、输出、状态和耗时
- **Artifact Record**: 一条稳定文件归属记录，表达输入文件或工具输出文件与 run、工具调用之间的关系以及文件稳定引用信息
- **Run Summary Metrics**: run 收口时形成的执行级聚合结果，表达该次执行的统计指标、终态和最终摘要，供诊断与概览查询复用

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在验收样本中，100% 的执行账本查询都能直接返回该次执行的终态、模型调用顺序、工具调用顺序和产物列表，无需人工拼接多处日志
- **SC-002**: 在验收样本中，100% 的工具输出文件都能追溯到唯一的父级 run 和唯一的来源工具调用；100% 的输入文件都能追溯到唯一的父级 run
- **SC-003**: 在验收样本中，100% 的失败、超时或主动停止执行都保留终态信息以及失败前最后一个已记录关键步骤，能够支持问题复盘
- **SC-004**: 在工具治理验收样本中，负责人可以在 3 分钟内查看任一指定工具最近 100 次调用的输入、输出或结果摘要、状态与耗时，而不需要查原始执行日志
- **SC-005**: 在包含同批并发工具调用的验收样本中，100% 的样本都同时保留原始分发顺序和可区分的真实执行时间线
- **SC-006**: 在持久化异常验收样本中，只要主执行逻辑本身可以完成，100% 的用户任务都不会因为单个账本记录失败而被直接中断
- **SC-007**: 在持久化异常验收样本中，100% 的账本写入失败都能留下可检索错误日志，且能反映到执行账本失败计数或成功率统计中，便于内部运维识别异常趋势

## Assumptions

- 当前单次请求唯一标识在一次执行范围内保持稳定，可继续作为首期对外可查询的 run 唯一身份
- 当前工具调用唯一标识和现有 `ToolArtifactRegistry` 已足够表达工具产物归属，不需要另起一套文件生成协议
- Java 主链路现有的请求进入点、模型调用点、工具分发点、工具完成点和顶层收口点足以挂接执行账本写入
- 本期验收以持久化事实与最小查询能力为主，不要求同步交付新的前端展示页面
- Workflow 执行链路允许沿用现状，待后续独立评估是否接入同一执行账本模型
- 执行账本默认运行在受控内部排障场景，首期不额外交付字段级脱敏规则或面向外部角色的安全展示策略
- 首期存储容量与数据库增长由现有运维体系兜底，本特性不额外交付生命周期治理能力
- 旧消息账本与旧会话正文账本不再作为本特性的真相源，本期也不承担把新执行账本兼容回旧模型的责任
