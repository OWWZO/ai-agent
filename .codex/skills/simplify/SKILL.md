# simplify

将最近改动过的代码收敛得更清晰、更一致、更容易维护，但绝不改变既有行为。

## 适用场景

- 用户明确要求“simplify / 简化 / 收敛 / clean up”刚写完的代码
- 一轮实现已经完成，但代码还有明显的重复、嵌套、命名不清或结构发散问题
- 需要在不改功能的前提下，把改动整理得更像可长期维护的正式代码

## 硬性约束

1. **绝不改行为**
   - 不改变功能、输入输出、副作用、异常语义、持久化语义、接口契约
   - 不顺手引入“看起来更好”的功能性修复，除非用户明确要求

2. **只处理最近改动范围**
   - 默认只关注当前会话刚改过的文件、当前 diff 中的代码、或用户明确点名的范围
   - 不要把一次 simplify 扩散成跨模块的大重构

3. **遵守项目规范**
   - 先服从 `AGENTS.md`，再服从根级 `CLAUDE.md` 与相关模块约束
   - 遵守现有 DDD 分层边界，不把业务逻辑塞进 `trigger` / `app` 等不该承载业务的层
   - 文件读写保持 UTF-8；复杂逻辑和边界条件使用中文注释，避免无意义注释

4. **优先可读性，不追求炫技**
   - 明确代码优于过度紧凑代码
   - 禁止为了“更短”而引入难读写法
   - 避免多层嵌套三元表达式，多个分支优先使用清晰的 `if/else` 或 `switch`

5. **优先复用，不重复造轮子**
   - 优先复用现有工具、公共方法、领域能力、配置装配和成熟库
   - 不为一次 simplify 新造抽象层，除非抽象本身明显降低复杂度

## 重点检查项

### 结构收敛

- 减少不必要的嵌套和分支层级
- 把过长函数拆成职责单一、命名清晰的小方法
- 把重复逻辑收敛到已有能力或局部辅助方法中
- 用更清晰的数据结构替代绕弯的控制流

### 可读性提升

- 用语义化命名替换含糊变量名、方法名、布尔标记
- 删除解释“显而易见代码”的注释
- 为复杂边界、业务原因、兼容性处理补上简洁中文注释
- 保持同一文件内命名、判空、返回风格一致

### 维护性优化

- 消除无意义中间变量、重复判空、重复分支
- 提取真正复用或能明显降低理解成本的辅助方法
- 保留有价值的抽象，删除只增加跳转成本的薄封装
- 保持错误处理路径清晰，不要把异常链路写得更隐晦

## 不该做的事

- 不做接口、SQL、表结构、持久化语义调整
- 不做和当前改动无关的格式化扫全仓、批量重命名或大面积重排
- 不把 simplify 变成“顺手重构整个模块”
- 不为了 DRY 牺牲可理解性
- 不把多个职责强行压进一个函数或类

## 推荐流程

1. 先识别最近改动范围
   - 查看当前 diff、最近 touched 文件、或用户明确指定的目标文件
2. 找出最影响理解成本的问题
   - 优先处理重复、嵌套、命名、职责混杂、风格不一致
3. 做最小必要重构
   - 每次修改都要能解释“为什么更清晰”，而不是“为什么更短”
4. 做针对性验证
   - 运行与改动范围匹配的测试、构建或 lint，确认行为未变
5. 只汇报重要变化
   - 说明哪些地方被收敛、为什么更易维护、还有哪些风险未验证

## 分语言提醒

### Java / Spring Boot

- 维持 DDD 分层边界，避免跨层泄漏实现细节
- 优先抽取领域内聚的方法，不要把领域规则回填到 Controller、配置类或启动装配
- 如果只是 simplify，不要无故碰 PO / DAO / Mapper XML / schema 等持久化链路

### TypeScript / React

- 保持现有组件边界和数据流方向清晰
- 优先显式 `Props`、清晰状态命名、稳定渲染分支
- 不默认引入额外 hook 优化或“聪明写法”来换取更少代码

### Python

- 保持输入输出边界清晰，避免隐式共享状态
- 优先把脚本式拼接改成职责明确的小函数，但不要过度抽象

## 产出标准

完成后的代码应满足：

- 读者更容易一眼看懂主要意图
- 结构更稳定，后续更容易继续扩展
- 行为完全不变
- 变更范围克制，只覆盖本次真正需要收敛的部分

如果无法在“不改行为”和“更清晰”之间同时满足，就优先保持行为不变，并向用户说明原因。
