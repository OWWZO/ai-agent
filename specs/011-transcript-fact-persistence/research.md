# Research: 后端事实对话账本重构

## Decision 1: 继续复用现有三张历史表，不新增独立文件表

- **Decision**: 保持 `ai_agent_conversation`、`ai_agent_message`、`ai_agent_message_event` 三张表，生成文件摘要直接落到 `ai_agent_message.generated_files_json`，不新增专门的文件表。
- **Rationale**: 用户明确要求能够直接查询每轮或每个会话生成过哪些文件，而不希望从事件载荷里二次提取。把轻量生成文件摘要落到消息表即可满足查询诉求，同时避免再引入新的文件表和跨表一致性问题。
- **Alternatives considered**:
  - 新增 `ai_agent_generated_file` 明细表：查询方便，但增加表、DAO、Mapper、事务一致性和迁移成本，用户已明确不需要
  - 仅保留事件载荷中的文件引用：续聊可用，但查询某轮生成文件时仍需解析 payload，不符合目标

## Decision 2: `ai_agent_message_event` 改为“语义事实块账本”，不再保存前端快照真相

- **Decision**: 事件表继续保留，但语义从“最终可见 UI 块快照”收口为“后端事实块”。每条记录只表达一次真实发生的语义事实，例如思考、计划快照、工具调用、工具结果和产物引用。
- **Rationale**: 用户需要的是后端记住做过什么，而不是后端帮前端记住它当时如何组织页面。事实块账本可以同时服务于历史详情和续聊上下文恢复，避免同一份数据既像历史 UI 快照、又像工作记忆输入的混合职责。
- **Alternatives considered**:
  - 继续保存最终可见 UI 快照：历史展示方便，但续聊和查询语义都要再猜测一次
  - 新增独立 block 表：概念更纯粹，但用户已明确不希望再加新表

## Decision 3: 历史详情由后端投影成实时同款契约，而不是前端再做大量补形

- **Decision**: 数据库中只保存后端事实；历史详情 API 在读取时把事实块投影为与实时对话一致的 canonical payload，前端继续走现有渲染链。
- **Rationale**: 这同时满足“数据库不存前端信息”和“前端效果不变”两个目标。后端掌握事实语义，也最适合集中完成历史到渲染契约的投影，避免前端维护越来越多的 history-only 修补逻辑。
- **Alternatives considered**:
  - 前端读取事实后自己投影：前端复杂度会继续上升，而且会把后端语义规则泄漏到 UI
  - 直接把数据库 payload 按实时协议存储：实现快，但本质上还是在存前端协议

## Decision 4: 大体量结果只保存稳定引用和必要元数据

- **Decision**: HTML、Markdown、PPT、代码文件、报告等大体量内容不再内联全文写入事件载荷，只保存稳定 `resourceKey`、预览/下载入口、文件类型、大小、缺失状态等必要信息。
- **Rationale**: 用户明确不想让历史表继续塞满文件正文。稳定引用更符合“后端事实落库”的语义，也便于后续文件缺失态处理和存储成本控制。
- **Alternatives considered**:
  - 在 payload 中保留裁剪后的正文片段：可读性更强，但仍会让事件载荷持续膨胀
  - 完全不保存任何文件元数据：续聊和历史展示都无法知道该轮产物是什么

## Decision 5: 会话记忆恢复与历史详情共享同一份事实语义

- **Decision**: `SessionTranscriptBlockAssembler` 直接消费新的事实块账本，`ConversationReplayAssembler` 也从同一账本投影历史详情；两条链路共享事实语义，但各自负责不同输出形态。
- **Rationale**: 这是避免“前端看得到、模型用不到”再次出现的关键。只要历史详情和工作记忆都围绕同一份事实账本工作，就不会再出现存的是一种东西、读的时候又拼成另一种东西。
- **Alternatives considered**:
  - 历史详情和工作记忆各维护一套事件解析器：实现快，但长期必然漂移
  - 只改历史详情、不改工作记忆：无法解决用户对“会记住之前对话”的核心诉求
